# Performance cost facts

Loaded when a session touches an AST-processing module, `Core/OpsConcrete.hs` or anything under `bench/`; a human arrives from the pointer in the root `CLAUDE.md`'s Performance model section, which keeps the rules for *reasoning about* these numbers — criterion-only, slopes not means, attribution by controlled experiment — resident beside that pointer.

File:line citations were verified against the tree at commit `2d16de4e7` (2026-08-14); the citation pass proves a cited line exists — this stamp, that it still says what the claim around it needs.

Cost facts worth knowing before optimizing:

- **The two AD pipelines have different cost shapes.** `cgrad`/`cvjp` re-run differentiation on every call; the symbolic tools (`grad`/`vjp`) pay tracing + `simplifyUserCode` + AD + `simplifyArtifactRev` once — a roughly size-independent overhead — then only interpret the artifact per call. Intended usage: build the artifact once (`vjpArtifact`/`gradArtifact`/`revArtifactAdapt`), interpret it many times (`vjpInterpretArtifact`); a benchmark calling full `vjp` per iteration conflates pipeline cost with execution cost.
- **`sreplicate`, `sreplicateN`, `stranspose` are metadata-only** (stride tricks; ox-arrays `X.replicate` is stretch-to-stride-0), and the ox-arrays dot and elementwise kernels (`Data.Array.Strided.Arith`) are stride-aware. Broadcasts and transposes fed into a dot or a `*` do **not** materialize, so don't rewrite them away on the assumption that they allocate.
- **`tssumN` is iterated `tssum`** (`Core/OpsConcrete.hs:222`): one full pass and allocation per summed dimension.
- **Interpreted `sgather` dominates gather-heavy programs** (the im2col patch arrays of convolution gradients — often ~two thirds of runtime). It runs through ox-arrays' `mgenerate`: per output position (the `shm` dims) evaluate the index and copy a slice (the `shn` dims); the per-element `Int` index arithmetic is the hot loop. One level down, the per-step cost is orthotope's run-decomposition of each strided slice (`toVectorListT`, worth pinning to orthotope-0.1.8.0, the version this repo's plan resolves — though it resolves it from the sibling checkout, which carries that version number plus the fix below — since the name is absent from 0.1.7.2), with a per-element fallback when the innermost dim is strided. That fallback has been replaced in `../orthotope`, which is ahead of the release, not stale: on `speedup-strided-tovector`, at `5e4ece1` and to be offered as a PR though none is filed, the via-a-list path becomes one `vGenerate` over precomputed run base-offsets, a single `quotRem` per element in place of a multi-index decomposition, measured on a replica of that path over twenty-odd strategies and thirty-odd shapes at a geomean 0.173× the old fallback with no regression on any shape (that `bq-expand` form is the last candidate since 2026-08-22: `mut-odo-vecdims`, a mutable odometer fill needing a new `Vector` method and possibly a stride-conditioned redirect, is the decided implementation, at 0.054 on the same replica, and every figure below is the `bq-expand` build's until re-measured) — and `cabal.project.local` currently carries an active `packages: ../orthotope`, so a build here links the fix, and the figures below are from that build unless marked *released*. Measured against the released fallback (2026-07-31, three interleaved A/B pairs over `gather48`/`scatter48`, the builds differing only in which orthotope they link, per-iteration OLS slope, every fit R² ≥ 0.99, control moving 0.7%), the fix is worth 3.96–5.57× on the two-gather chains and 4.7–7.1× in allocation, and on the conv sweep itself 1.6× at `6x6` rising to 3.5–4.2× from `24x24` up, at 2.1–6.5× less allocation; the *fused* variants, which never reach the changed code (byte-identical allocation), appeared ~18% slower in that A/B — a position effect of leftover RTS pool state, not the fix: the account is in `docs/position-effect.md`, the pin-the-selection rule in `bench/CLAUDE.md`. Two benchmark-confirmed consequences, both remeasured across that fix and stronger after it: (1) `contractAst` sorts a gather's `shn` dimensions ascending, via metadata-only compensating transposes, so the largest dimension is innermost and the copy's inner loop amortizes the per-step overhead — worth 1.67× in time (released: 1.27×), and it halves allocation too, 4.93MB against 9.44MB per iteration on `gather48` (released: 35.05MB against 44.36MB, a 1.27× gain and no halving — so it is not only a copy-amortization win) — while reordering the `shm` dims, by contrast, changes nothing, in time or in allocation; (2) fusing two gathers into one is a *pessimization* — it trades few large-slice copies for many tiny ones while `mgenerate`'s cost is per position — costing 10.5× (released: 2.25×), so the phase-gating that prevents that fusion is intentional, and sorting cannot rescue the fused form (its `shm` order measures flat, the `fused-gather-shm-sorted-*` benches; its `shn` is tiny and already sorted, fusion having consumed the large dims into the index function). Reducing the remaining cost had two candidate designs and neither is now open work. The upstream one was two-stage: its first stage is the fallback fix above, which has shipped and been measured, leaving only its second, a C strided copy in ox-arrays' cbits ([#123](https://github.com/Mikolaj/horde-ad/issues/123) material). The other, the client-side add-zero gather — gather rebuilt on the scatter model, each strided slice densified through the stride-aware C arith kernels by adding a replicated scalar zero (normalize-in-C with a fused redundant add) — is refuted rather than pending: it needed no upstream release, but the `scatter48` bound that priced it at ~9–12× was measured away by that same fix (scatter bullet below), so do not build it on those numbers.
- **Concrete scatter is slice-based and cheaper than gather on the same index map and strided-read workload — 2.55× against gather's natural orientation, 1.32× against its fastest** (`scatter48` ~0.5ms), and cheaper in allocation too, 3.87MB per iteration against gather's 9.44MB — which measures what the interpreter builds per position rather than elements moved, so it sharpens the claim rather than contradicting it. Against *released* orthotope the time gap was ~9–12× (`scatter48` ~0.55ms vs `gather48` ~5–7ms), an order of magnitude that was a property of the released fallback and was measured away by its fix (gather bullet above), scatter itself unmoved — so any design priced against that headroom is priced against numbers that are gone. As gather's transpose it performs the same element transfers and, where the index map is many-to-one, even more arithmetic — it sums where gather copies — so the gap is code path, not data volume. The path: `tscatterZSScalar` (`Core/OpsConcrete.hs:1581`) does per-position index eval + `IntMap.insertWith (+)` with whole-slice adds through the stride-aware `NumElt` C kernels, then flat `VS.copy` write-outs — the interpreted Haskell is per *chunk*, all element traffic is C. The accumulation is what dodges the Haskell strided-normalize (it consumes strided views in C and leaves dense buffers to memcpy), a trick the current gather doesn't borrow, though the add-zero design above shows how a sum-free gather could: force a redundant add. Corollaries: extending the `shn`-sort to scatter is an outright pessimization — measured ~4.7× in time against released orthotope (`two-scatters-ad-shn-sorted`, 2.59ms vs 0.55ms; the fix moves only the sorted variant, its slice views being the only scatter traffic that reaches the fallback) and ~3.7× in allocation on the current build (14.40MB vs 3.87MB; released, 17.66MB against 3.91MB, 4.51×) — each slice is added as one flat vector, so a sorted `shn` has no per-`shn`-dim loop to amortize, while the compensating transposes leave the slice views strided; scatter in its natural orientation is the empirical bound for a fast gather path (its strid-ified and fused forms are far slower); and a rewrite's whole-program effect grows with problem size, converging toward the dominant op's win (the `shn`-sort is negligible on small overhead-bound nets, ~17% on a 24×24 CNN gradient once gathers dominate).
- **`vjpArtifact` does not run `contractAst`** — it runs `simplifyUserCode` + `revProduceArtifactDt`; `contractAst`'s only caller is `simplifyInlineContract` (`Core/AstEngine.hs:52-56`, which applies `contractAst` twice), and `simplifyInlineContract` is in turn what `simplifyArtifactRev` and its `Fwd` sibling apply to artifacts — and what convVjpBench's handwritten-term variants call directly, on a term rather than through an artifact. Outside its definition in `Core/AstTraverse.hs`, the name occurs only at that one call site and in `bench/ConvVjpBench.hs` comments. Hence the *raw* artifact is contraction-independent — which explains `S-exec-raw`'s role as an A/B control and means "artifact" benchmarks measure different pipelines depending on whether they stop at `vjpArtifact` or add `simplifyArtifactRev`.

Adding a `contractAst` rewrite rule: put it in `contractAst`, not a smart constructor (which fires in every phase and reshapes intermediates other rules match on), applied at a node's exit and *after* any case that hoists structure out of the same constructor and re-enters `contractAst`. Make it idempotent, and identify which existing rules could undo the form it introduces — for the `shn`-sort, `astTransposeS`/`astGatherKnobsS` only absorb *leading*-dims permutations while the compensating transposes permute trailing dims — recording that argument as a code comment at the rule.
