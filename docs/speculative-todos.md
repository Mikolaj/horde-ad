# Speculative TODOs

Unvetted ideas from a 2026-08-14 review of the documentation-and-verification system, saved so they need not be re-derived. None is a commitment, none has been costed beyond a sentence, and any may die to a measurement — when one does, record the ruling here so it is not re-proposed. The common thread: convert remembered discipline into mechanism that fires, since the recorded failures of this system — the unwrap-rewrap cycle, the rules file that never loaded, the stamp that sat orphaned for eleven days — are each a case of remembered discipline failing while every mechanical check stayed green. Scope varies by item: some are this repo's, some user-scope, some span the repos sharing the tools.

1. **Anchor citations to content, not line numbers.** The prose rule already exists ("carry a distinctive phrase; a line number does not survive a reflow") — apply it to code citations. Store the expected snippet, or its hash, with each `file:line` and let `tools/check-plan-citations.py` compare rather than merely resolve; or replace line numbers with unique anchor strings the checker locates. This closes the "a citation that resolves can still lie" class mechanically — today the eyeballing of printed snippets is the one part of pass 1 still resting on a reader — and a legitimate drift then flags for restamp instead of passing silently. Small effort, probably the largest remaining accuracy hole.

2. **Make claims executable where they are checkable.** Pass 3 is expensive because quantified claims live as prose and every verification re-derives the greps. Attach the evidence to the claim: an inline check block (command plus expected result) beside each only/every/count claim, and a runner that executes them all — `tools/check-doc-examples.py`'s `>>>` mechanism generalized from Haskell outputs to arbitrary claims. Stamps then become per-claim, drift cannot be silent, and the human reading shrinks to the unmechanizable residue. The six-counts-falsified-in-a-day incident is the case this answers.

3. **Fire rulings and lazy context from hooks, not path frontmatter.** The path-keyed load is measured-undependable and nothing announces its absence; hooks are deterministic. A PreToolUse hook matching edits under the performance-relevant modules can inject a one-line pointer to `.claude/rules/performance-model.md` with certainty, and the don't-do rulings — whose whole purpose is firing at the moment of re-proposal — could live in a small pattern-to-ruling table a hook greps against commands and diffs (gather fusion, `-A64m`, `--no-gpg-sign`, `stash pop`), surfacing the one-line ruling exactly when someone starts to violate it. Tripwires beat residency on both probability and token cost. User-scope mechanism; amends the migration ruling's *mechanism*, not the ruling.

4. **Verify at the events that cause rot, not on request.** Stamps orphan at rebases, twins drift at edits, claims rot at pushes — hang the checks there: a `post-rewrite` git hook running the stamp check, `pre-push` running the checker suite and the self-tests (seconds, now that they exist), and a periodic doctor session for the sampled deep passes. The orphaned bench stamp would have been caught the minute of the squash.

5. **Re-measure the environment almanac instead of trusting it.** The portable notes are largely executable facts — `pkill` self-matching, the phantom dotfiles, `gpg` under the sandbox, the ugrep shim's quirks. One environment-selftest script probing the top facts, run occasionally and on Claude Code version changes, gives the machine notes what the checkers got: a control that cannot expire silently. Today they have no instrument at all and break invisibly on harness updates.

6. **Mechanize the printed-AST oracle into affected-set benchmarking.** The "can this rewrite affect that program" trick is the cheapest decisive instrument in the performance model, applied by hand. A script printing the canonical artifacts of the benchmark suite's programs under both builds and diffing them would settle affects-nothing claims in one command and shrink collections to the affected set — most of a long `convVjpBench` run avoided when churn is localized. Pairs with committing measurements as JSON artifacts that prose cites by ID, dissolving the provenance clauses the cost-facts bullets used to carry.

7. **Stop having twin tools.** `tools/check-twin-sync.py` patches the symptom; the cause is vendored copies. The isolated config blocks are most of the packaging work already done: one shared doc-tools sibling checkout on the model of `../ox-arrays`, with per-repo config files, ends the porting debt permanently and retires the sync checker.

8. **Test the guidance itself, so the corpus can shrink.** The user-scope `CLAUDE.md` is a layer that dies with each model generation, but it only grows. Point the blind-walk instrument at rules: run a fresh session through a recorded failure scenario without the bullet and see whether the current model still errs; a bullet the model no longer needs retires with evidence. Residency is the system's largest recurring cost and this is its only principled deletion mechanism so far.

9. **A CI step running the citation checker.** Of the mechanical passes, `tools/check-plan-citations.py` is the one CI can run — self-contained on git and the tree, needing neither the sibling checkouts nor wrap80 — so a seconds-cheap step in `lint-and-test-suites.yml` over the stamped documents would catch an orphaned or stale stamp at push time, from any machine. This is the narrow, do-now member of item 4's family: the git-hook variants cover only the machine that installs them.

If only two: item 1 for accuracy per unit effort, item 3 for making the anti-re-proposal goal — the one the rulings genre exists for — nearly deterministic.

## Maintainer options against the small-pinned churn tax (2026-08-18)

The session-closing answer, verbatim, to "assuming a GHC fix is not coming soon and convVjpBench and gradbench are fully representative, what are my options?" — unvetted like everything in this file; the measurements behind each claim are orthotope's `micro-regime3/small-pinned-churn-investigation/nursery-position-findings2.txt` items 30–44.

A decision brief, all from this session's measurements, taking the pipeline split (item 43's pipeline reading) as the organizing fact — because under your "fully representative" assumption it's the thing that forbids one perfect answer:

**Short term — documentation and flags, zero code:**

1. **Retire `-A1G` everywhere it's baked or advised.** It lost on every axis measured: the real suite (126.6 s / 26.2 GB vs -A32m's 117.7 s / 2.85 GB), the CNN gradient (worst arm on all three nets), gradbench (never necessary). This much is unconditional.

2. **For a single recommendation, the choice is -A32m vs -A64m.** `-A32m` is the measured winner for the saturated mixed regime, the real suite, and symbolic-pipeline code (conv −9%, lstm −9.5%), at ~3 GB-class memory; its cons are the cgrad class (particle +18%, kmeans +37%) and the known imagenet-scale kernel pathology (README floor section — anything with ~29M-element tensors wants ≥64m). `-A64m` is never best but never far off (worst measured ~+17% on kmeans), dodges the imagenet edge, and is the safer *blind* default. My read: advise **-A32m for programs using the symbolic pipeline, -A64m as the don't-know default, -A64m+ for cgrad-heavy programs** — and since library `ghc-options` can't set users' RTS anyway, this is a docs table, not a build change; only your own suites' `exe-options` actually move (where CAFlessTest says -A32m; convVjpBench's `-A1G` should stay until you deliberately recalibrate its recorded properties, since it's measurement infrastructure, not advice).

3. **Advertise `-A4m -AL64m` as the specialist setting**: the outright fastest for artifact-interpretation hot loops (−14–18% on the CNN gradient vs baked) and the lowest memory, at the price of +22% user CPU and being actively bad for cgrad code (+40–54%). It's the session's novel knob and costs users one flag to try.

**Medium term — the one code change that earns its keep:**

4. **Padding small pinned results in the stack's allocation path** — but be precise about what it buys. Measured pros: it kills the *burst* route completely (the in-binary control: zero tax at every area), costs ~zero time (pad ≈ base within the A/A band everywhere) and bounded memory (≤ ~3 KB/vector), and — the part that matters most to *you* — it restores **benchmark and hot-loop integrity**: criterion processes and repetitive training-loop phases are exactly where the +27–44% lives. Measured cons: it does **not** protect heterogeneous phases (the interleaved route is class-independent — items 37/39/45 — so real mixed programs stay at their degraded level regardless), it entrenches defeating a GHC mechanism (your issue argues this explicitly, which is coherent as long as you ship it disclosed), and the 3276-byte constant becomes a magic number you maintain. I'd ship it behind a toggle, framed as "hot-loop and benchmark hygiene", not as "fixes the condition".

5. **Skip unpinned small vectors.** Item 45 is decisive here: unboxed allocation *still poisons via the interleaved route* (+23% at 32m, +8.6% at 1G), so unpinning buys the same protection scope as padding — burst route only — at far higher cost (the C kernels need `Ptr`, so small arrays would need copy-to-pinned at every FFI call or a pinned-scratch-reuse scheme; a representation change either way). Padding dominates it on current evidence.

**Long term:**

6. **The interleaved route is the strategic problem and no allocation policy reaches it** — its only user-side levers are the -A choice and *allocating less in hot paths at all*. That makes the existing #123 direction (the C strided copy in ox-arrays cbits, fewer small intermediates per gather) doubly valuable: every intermediate removed helps both routes. That's the durable engineering direction while the RTS fix is pending.

7. **The filing remains the real fix** — the issue's correction directions (accumulator recycling/isolation, and the Note's own periodic nursery reallocation, which alone reaches both routes) are what would eventually let all of the above be deleted, which is worth saying in your docs so the workarounds read as dated, not permanent.

The follow-up cross-matrix, same session: which of the brief's options above also fix the other known problems — per problem, per option, with one untested interaction flagged honestly.

**27601 (the own-group pool doubling) — its horde-ad impact being the convVjpBench position effect and the memory doubling; its micro-regime3 impact being minor (findings item 29 measured own-group sprays harmless in the accumulator sense; the tables' real deflation is the small-pinned condition):**

1. **The brief's options 1–2 (retire -A1G, run 32m/64m) substantially fix it** — 27601's mechanism *needs rare collections* to accumulate the gigabyte of block groups between GCs, which is precisely what `-A1G -I0` provides; at 32m/64m the accumulation window shrinks 16–32×, so both the doubling and the 22%-class coupling shrink with it. Bonus: the same move kills the **alone-slope honeymoon transient** wholesale (it exists only at areas past L3), so criterion alone legs become honest again — two known problems for the price of one flag.
2. **The brief's option 3 (-A4m -AL64m) is the one option with a plausible 27601-worsening vector, and it's untested**: raising the large-object allowance is literally permitting more own-group accumulation between collections. Findings item 32 probed only the small-pinned poison under -AL, not an own-group spray. The exposure is bounded by the -AL value (~64–128 MB of checkerboard, not a gigabyte), so probably mild — but if you advertise the setting, that's a cell worth running first.
3. **The brief's option 4 (padding) converts rather than fixes**: padded vectors *are* own-group traffic, so at large areas padding trades the worse condition for 27601-class exposure; combined with the brief's options 1–2 (no large areas) the converted traffic is mostly harmless upfront — but findings item 44 says interleaved own-group still poisons at 32m, so no free lunch there. Also note: if ox-arrays adopts padding, micro-regime3's arms stop modeling the shipped path until its replicas are updated — a benchmarking-validity cost specific to micro.
4. **The brief's option 6 (allocate less in hot paths) mitigates everything** — 27601, the churn tax, both routes — it's the only universal user-side lever.
5. **The brief's option 7 (the filings)**: the two issues' correction lists overlap in exactly one direction that kills *both* conditions — **a separate region for pinned allocation** (27601's correction 3) together with **periodic nursery reallocation** (the Note's own fix, which repairs the victim side of both). Worth emphasizing in advocacy that these two reach everything, where accumulator recycling alone fixes only the new condition.

**The other known problems, quickly**: the convVjpBench *suite's* own coupling is fixed by measurement practice (per-bench processes, already in position-effect.md), but a deliberate recalibration of the suite to -A32m would buy integrity against both pool conditions *and* the transient at once — the one recalibration that retires three instrument hazards together; parallelTest's ~50 GB peak falls mostly out of the brief's options 1–2 by arithmetic (per-capability nurseries × 16); the imagenet -A32m kernel pathology is dodged by the brief's option 2 (-A64m as the blind default) and is the standing reason its option 1 cannot be unconditional; and the interleaved degradation, as the brief said, yields to nothing but the brief's options 2 and 6 — the -A choice and allocating less.
