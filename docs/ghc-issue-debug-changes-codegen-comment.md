# GHC issue comment: what the debug option moves, and how it relates to the latch item

Staged and posted 2026-09-11 as [a comment](https://gitlab.haskell.org/ghc/ghc/-/work_items/27687#note_697268) on GHC work item 27687 ([ghc-issue-debug-changes-codegen.md](ghc-issue-debug-changes-codegen.md) is its filed record); this file stays as the record of the comment, the text from "#27799 reports" down being the body as posted --- under a one-line preface and inside a `<details>` block, neither of which is carried here. It refers to [GHC work item 27799](https://gitlab.haskell.org/ghc/ghc/-/work_items/27799), whose filed record is [ghc-issue-latch-loses-fallthrough.md](ghc-issue-latch-loses-fallthrough.md). The prose is ASD-STE100 Simplified Technical English.

#27799 reports a different defect, and it starts at the same choice in the compiler as the code change that this issue shows. That is the reason for this comment: the choice is what this issue is about, although the report does not name it, and the two items together show what it costs.

The difference that `-g1` makes in this module is one choice in the linear register allocator, and the debug information has no part in it. The head of the loop is a join with two arms: the entry to the loop, which has the frequency 0.375, and the return into the loop, which has 1.125. `joinToTargets` keeps the assignment of the first jump to a block and makes fixup code for each later jump, thus the arm that is second in the processing order is the arm that gets a fixup block. The option exchanges the two arms in that order.

The measurement, on 9.12.4 at `-O1`. The two builds have the same control flow graph, the same sixteen edges with the same frequencies, and they differ in the position of the fixup block only. Without the option the fixup is on the return arm, thus inside the loop, and it is five moves. With `-g1` the fixup is on the entry arm, thus outside the loop, and it is three moves and a jump. `-ddump-cfg-weights` names the edge that each fixup block is on, and `-ddump-asm-liveness` shows the two arms in the opposite order in the two builds. That one instruction is the difference in the count that the description of this issue gives.

The processing order comes from `sccBlocks`, which numbers its vertices in the order of its input, and that input is the entry block and then the blocks of the procedure in the ascending order of their uniques. Thus any input that moves the uniques can move this choice, and a debug option is one such input.

The TODO for this is in #17864, which keeps the TODO list of the NCG NOTES file that was removed from the tree: "picking the assignment on entry to a block: better to defer this until we know all the assignments. In a loop, we should pick the assignment from the looping jump (fixpointing?), so that any fixup code ends up *outside* the loop." That is what this module needs. With the assignment taken from the looping jump, the fixup code is outside the loop in both builds, and the option has no instruction to move.

How far the two items go together. In #27799 the join is the exit block of a loop and not its head, and the position of the fixup has no price of its own there: it decides which predecessor of the exit block wins the fall-through in block layout, and the loop then makes one more jump on each iteration. The module of this issue has no loop with its test at the bottom, thus it does not show that defect. The reproducer of that item does carry fixup code inside loops, thus one program can hold the two conditions together. So the two items have one cause and two effects, and one correction does not serve both: a deliberate assignment choice corrects this item, and the other item needs a change in block layout also, because its latch loses the fall-through each time that its exit block has a second predecessor, whichever arm the fixup is on.
