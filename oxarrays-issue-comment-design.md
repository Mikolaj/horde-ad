# Comment for the ox-arrays issue (draft): the design

*(Draft of the single design comment on the ox-arrays issue drafted in `oxarrays-issue-description.md`. Links to be filled in when filing.)*

## The design

This is staged: a pure-orthotope fix to the strided fallbacks first, an ox-arrays C kernel for what that cannot reach. The first stage is done and will be offered as an orthotope PR (branch `speedup-strided-tovector`, [micro-regime3 README][readme]) — faster than the old fallback on every benchmarked shape, a geomean of 0.173× its time, measured on a replica of the path. It settles what pure Haskell can do here rather than ending the matter: of the strategies benchmarked, the fastest is only ~1.5× beyond it and needs orthotope's `Vector` class to grow a mutable fill, and none of them changes that regime 3 has no contiguous runs to slice, so the transfer stays per-element in Haskell. That is what the second stage moves into C.

**A strided-copy kernel in the existing cbits**, writing directly into the destination buffer at an offset. Unlike the arith kernels it is type-agnostic — it needs only an element byte-width, no per-type TH families — and the existing wrapper plumbing shows how to bind most of it: `wrapUnary` in `Data.Array.Strided.Arith.Internal` already hands C a shape, strides and an offset pointer, though its offset is into the *source* and its destination is a freshly allocated dense buffer, so writing into a caller's buffer at an offset is the part with no precedent there. In spirit the walk already exists: the `_sv_strided` arith kernels traverse arbitrary strides and write densely, and a strided copy is that walk minus the arithmetic — which a client could exploit today by densifying each slice through a scalar-zero add via `wrapBinarySV`, though at the margin measured in the issue that detour no longer pays for itself.

Gather-heavy clients then get fast with no client-side changes: `mgenerate`'s per-position Haskell overhead remains, but it is per position, not per element, and the scatter numbers bound the expected effect. That bound is now much tighter than it was: against the released fallback the same traffic ran in ~0.5ms through the C kernels where gather took ~5ms, but with the fix above gather is at 1.29ms in its natural orientation and 0.69ms in its fastest, against scatter's unmoved ~0.5ms — so ~1.3–2.5× is what a strided-copy kernel has left to win here, not the order of magnitude the released numbers suggested. Dynamically switching between per-element and per-slice implementations should be unnecessary: one code path degrades gracefully, and where slices are tiny, per-position overhead dominates regardless.
