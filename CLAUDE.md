## What this is

horde-ad is a Haskell automatic differentiation library (reverse and forward mode) that supports array operations and generation of symbolic derivative programs. It is an early prototype and deliberately not coded defensively: code is expected to fail on cases not covered by current tests, and the fix is to add primitives/tests rather than defensive code.

Upstream stack: the array backend is ox-arrays (maintained by a horde-ad co-author) over orthotope. Mikolaj maintains horde-ad and, while not an orthotope maintainer, has a history of accepted orthotope PRs — equivalent standing when deciding where a fix should land — so performance fixes are planned across the whole horde-ad → ox-arrays → orthotope stack, orthotope changes going in as PRs to its maintainer. Orthotope deliberately contains no mutable code in the library it builds (a pure `Vector v` class API; its one `runST` module, `Data/Array/Internal/FastReshape.hs`, is not listed in its cabal file and so does not even ship in the released tarball, only in the checkout); that module's precedent means neither mutability nor needing a new class method any longer disqualifies a proposal for it, though its non-use keeps both weighing against one — ruling amended 2026-08-07 in the checkout's `micro-regime3/README.md`, mutable-ceiling section.

## Build and test commands

### Build

Development setup (fast builds, optimization off; guarded not to clobber an existing config):

    [ -f cabal.project.local ] ||
      cp cabal.project.local.development cabal.project.local
    cabal build

Run `cabal` (like all `git` writes and `gpg`) unsandboxed — `~/.cabal` is read-only under the inner sandbox (sandboxing notes below). A full build takes long: give Bash a generous timeout or run it in the background rather than concluding it hung. Local `cabal haddock` costs ~10 minutes even for a sublibrary (haddock re-runs GHC's front end over the whole library dependency, with the typelits plugins dominating typechecking) — prefer CI's `--haddock-all` step, which runs on every push.

Cabal flags: `with_expensive_assertions` (extra checks), `release` (set for Hackage releases; disables `convVjpBench`, the two live MNIST benchmarks and every test suite but `minimalTest`), `test_seq` (force parallelTest to run sequentially).

Source checkouts of ox-arrays and orthotope may be present as siblings (`../ox-arrays`, `../orthotope`) — whether a session sees them depends on the wrapper (sandboxing notes below); when hidden they report "No such file", and the released sources can always be unpacked from the cabal store instead (recipe in the build-and-shell-tooling notes). The kernels of interest are `mgenerate`, `Data.Array.Strided.Arith` and the `X.replicate` stride tricks.

### Tests

Tests are computation-intensive, so run them with optimization even though the dev config sets `optimization: False` for builds, and pass the flag on the command line (an unoptimized timing is not comparable to an optimized one — see Gotchas):

    cabal test minimalTest --enable-optimization  # short, no dataset needed
    cabal test CAFlessTest --enable-optimization  # sequential; doubles as a benchmark
    cabal test sequentialMnistTest --enable-optimization  # same
    cabal test parallelTest --enable-optimization 2>/dev/null  # RUN BY HAND ONLY, see below; large MNIST tests; stderr redirect keeps interleaved printf tidy
    cabal test fullTest --enable-optimization  # everything, sequentially

**Never run `parallelTest` from a session — it is Mikolaj's to run by hand, and he runs it regularly.** It is the one suite that can take the machine down: alone among them it is built `-with-rtsopts=-A1G -I0 -N8` and, alone among them, left parallel by using plain `testGroup` where the other four use `inOrderTestGroup`. It runs at 16 capabilities rather than the 8 that flag asks for, and no RTS setting changes that: tasty raises capabilities to its `NumThreads`, which defaults to `getNumProcessors` in tasty's `Test.Tasty.Options.Core`, via `when (ncap < nthreads) $ setNumCapabilities nthreads` in its `Test.Tasty.Parallel` — it only ever raises, so the baked `-N8` and even a command-line `+RTS -N2` are both overridden, while `--num-threads=8` does lower it. A passing run peaks at 49.9GB resident (measured, `/usr/bin/time -v`, 326 tests in 324s). On a 62GB desktop that leaves ~12GB, so anything else substantial running at the same time invites the kernel OOM killer — which has already killed both the suite itself and a browser alongside it here. `fullTest` covers a superset of its modules sequentially and is the safe way to get the same coverage; `test/ParallelTest.hs` repeats `TestConvQuickCheck.testTrees` four times to saturate cores precisely because of this hazard.

Run a single test with a tasty pattern — checking what it actually selects, the match being by containment (portable notes below); this one takes two, `gatherNested1` and `gatherNested12`:

    cabal test CAFlessTest --enable-optimization --test-options='-p "gatherNested1"'

To enumerate a suite without running it, `--list-tests`:

    cabal test minimalTest --enable-optimization --test-options='--list-tests'

Keep the flag on it as on every other invocation here: dropping it forces a full rebuild of the local packages (Build and shell tooling below), which costs far more than the listing does. The listing is how a count claim about a suite gets settled — `-p` selects on the test *name*, so a renamed test leaves its series without failing anything, and only the enumeration shows it. Don't pipe the listing through `head`/`tail`; truncating it is how a wrong count gets quoted.

The harness itself — the `testCommonLibrary`/`test/tool/` layout, why CAFlessTest must stay sequential, and how to refresh printed-AST expectations after a simplifier change — is in `test/CLAUDE.md`, which a session loads automatically when working under `test/`; a human must open it there.

### Lint and format

Two tools: `hlint .` (using the liberal `.hlint.yaml`) and stylish-haskell (`.stylish-haskell.yaml`; the editor runs it on save, and CI re-runs it over every tracked `.hs` file, pinned to the same release, since a formatter that disagrees with the editor is worse than none). In `.hlint.yaml` pass `-XNoStarIsType` (honored by the hlint on PATH, built from hlint master though it self-reports v3.10 — *released* binaries mishandle the flag, including the newest, v3.10, which reports 7 parse errors here, one per file importing `GHC.TypeLits (…, type (*))`, whether the flag comes from the config or the command line, which is why no CI job runs hlint) and `--cpp-define=WITH_EXPENSIVE_ASSERTIONS` and `--cpp-define=TEST_SEQ`, but not `--cpp-simple`, which cannot parse `Core/Types.hs` (a parse error at `pairWithNil`). The default CPP pass parses every file here, but it defines nothing, so it *drops* each `#ifdef`-guarded branch rather than linting it — hence the defines, which are what the tree's only guarded *code* needs to reach the linter at all: the two expensive-assertion blocks in `Core/AstInterpret.hs` and the `NumThreads 1` line in `test/ParallelTest.hs`. The nine `MIN_VERSION_GLASGOW_HASKELL` guards are left dropped, each protecting one `OPTIONS_GHC` pragma and no code, and no `#else` exists anywhere in the tree, so a define can only add to what hlint sees, never swap a branch. That covers all twelve conditionals — nine pragma guards dropped, three code blocks linted — and both cabal flags can be set at once, so what the defines spell is a configuration that builds rather than a program nothing compiles. `hlint .` stays at `No hints`, as do the passes with either define alone and with neither.

Stylish-haskell honors no `LANGUAGE` pragma that sits below a CPP conditional, and on a file it cannot parse it exits 1 and changes nothing — so the file is silently left unformatted, in the editor as much as in CI. `Core/AstSimplify.hs` had been in that state, its `UnboxedTuples` pragma sitting under an `#if`; the pragma is now above it, with a comment saying why. The extensions stylish does see otherwise come from the cabal file's `default-extensions`, found by searching upwards from the file, which is why `LambdaCase` is listed there.

### CI

Two workflows. `.github/workflows/haskell-ci.yml` (generated by `haskell-ci`, configured by `cabal.haskell-ci`) compiles the package, its five test suites and its benchmarks with GHC 9.10.3, 9.12.4 and 9.14.1, runs `minimalTest`'s `detSquare` tests, and then `cabal check`, haddock and an unconstrained build — every build, test and haddock invocation carrying `--disable-optimization`, which `cabal check` cannot take and which `v2-update` and `sdist` do not. Its test step is narrowed to that one suite because haskell-ci builds and tests an *unpacked sdist*, and `samplesData/` is tracked in the repo but not shipped in the package, so any suite reading MNIST data would fail there for missing files. Narrowed again by `-p "detSquare"` within that suite, because the step is unoptimized and `minimalTest`'s printed-AST expectations are not build-independent — which compiler transformation moves them, on which GHC versions, and which four tests fail is in the hunk comment in `.github/haskell-ci.patch`, the copy to read and to keep current. The filter buys correctness, not time, `detSquare9` alone being the suite's slowest test by far. No coverage is lost, the whole suite running optimized in the other workflow. `.github/workflows/lint-and-test-suites.yml` (hand-written) carries what that one cannot: stylish-haskell over every tracked `.hs` file, and, on 9.12.4 and optimized, the same sanity test followed by `shortProdForCI` in full and a full `convVjpBench` run whose allocation properties it then checks. Between them, unoptimized compilation and the sanity test are covered on three GHC versions, optimized compilation and the benchmark runs on one.

`convVjpBench` is protected twice: the generated workflow compiles every benchmark on all three versions, and the hand-written one executes the whole of that suite at criterion's default time limit with `--regress allocated:iters`, then runs `tools/check-conv-bench-props.py --allocation-only` over the JSON. Timing stays ungated — CI criterion numbers are too noisy for that, and the default limit is too short for the slopes anyway — while allocation is exact enough in the iteration count to gate at that limit; the per-benchmark figures the run prints also serve to date a suspicious number against an older log (`bench/CLAUDE.md`).

What CI does *not* check, so don't read a green run as covering it: `hlint .`, which no released hlint can even parse here (see Lint and format above), so it is a local check only; CAFlessTest and the other three suites, including every printed-AST test they alone hold — `minimalTest`'s own series is covered, the hand-written workflow running that suite optimized and with no `-p` — and the three remaining benchmark targets, all validated by local runs alone — of those suites, `fullTest`, `parallelTest` and `sequentialMnistTest` read MNIST data and so could not run in the generated workflow at all, while CAFlessTest could and is left out on cost, at 141s optimized locally and some eight times that unoptimized; expensive assertions, `with_expensive_assertions` defaulting to `False` and enabled by no workflow; and anything platform-specific, both workflows being Linux-only.

## Architecture

The library is organized around a final-tagless style: tensor operations are type classes (chiefly `BaseTensor`, `Core/Ops.hs:297`, whose superclass context starts twenty-three lines earlier) over a `target :: Target` type constructor, indexed by a type-level tensor kind `TK`. Objective functions are written polymorphically in `target` and then instantiated at one of three carriers:

- `Concrete` — plain evaluation on CPU arrays (backed by ox-arrays/orthotope). Defined in `Core/CarriersConcrete.hs`, instances in `Core/OpsConcrete.hs`.
- `ADVal target` — dual numbers for direct (tape-like) AD, generic over the underlying carrier. `Core/CarriersADVal.hs`, `Core/OpsADVal.hs`.
- `AstTensor` — symbolic AST terms. `Core/Ast.hs` (grammar), `Core/CarriersAst.hs`, `Core/OpsAst.hs`.

Tensor kinds (`Core/Types.hs`, `Core/TensorKind.hs`): `TKScalar r`, `TKR n r` (ranked: only rank in the type), `TKS sh r` (shaped: full shape in the type), `TKX sh r` (mixed), `TKProduct` (tuples); `TKR2`/`TKS2`/`TKX2` allow nested element kinds. In the user-facing surface (`HordeAd.OpsTensor*`) operation names are prefixed by variant: `r*` ranked, `s*` shaped, `x*` mixed, `k*` scalar, `t*` kind-polymorphic (`tlet`, `tpair`, `tproject1`). That reading does not carry into `Core/Ops.hs`, where `BaseTensor`'s methods mostly prefix the variant letter with `t` — `tssum` shaped, `trsum` ranked, `txgather` mixed, `tkconcrete` scalar — so a `t` there marks a class method, not kind-polymorphism; a handful keep the bare form (`rshape`, `kcond`, ...). The shaped, ranked and mixed styles interoperate freely; conversions are zero-cost (`Core/ConvertTensor.hs`, `Core/Conversion.hs`).

### Two AD pipelines (`HordeAd.ADEngine`)

1. **Non-symbolic AD** (`cgrad`, `cgrad2`, `cvjp`, `cvjp2`, `cjvp`, `cjvp2` — all six, each `2` variant returning the objective's primal result alongside the derivative, the unsuffixed one being `snd` of it): instantiates the function at `ADVal target`, generic over the carrier so that nested derivatives can be defined, `ADVal Concrete` being the usual instantiation. That genericity is why call sites carry explicit type applications, `@_ @_ @_ @Concrete`, and why the symbolic adaptors below are deliberately not generalized. Sharing is preserved automatically; permits dynamic control flow; differentiation happens on every call.
2. **Symbolic AD** (`grad`, `vjp`, `jvp`, `vjpArtifact`, ...): instantiates at `AstTensor`, differentiates the AST once into a derivative "artifact" program that can then be interpreted many times on different inputs. `grad`/`vjp`/`jvp` simplify it internally (`simplifyArtifactRev` and its `Fwd` sibling), while `vjpArtifact`/`gradArtifact`/`revArtifactAdapt` hand back the raw artifact and leave that to the caller — which is what the `vjpArtifact` cost fact in `.claude/rules/performance-model.md` turns on. Sharing must be marked explicitly with `tlet`.

Reverse-mode differentiation itself goes through **delta expressions** (`Core/Delta.hs`): a sparse representation of the linear map that is the derivative. `Core/DeltaEval.hs` transposes/evaluates it (`gradientFromDelta`, `derivativeFromDelta`, both exported at `Core/DeltaEval.hs:8`), related, for all `d`, `dt` and `ds`, by `dt <.> derivativeFromDelta d ds = gradientFromDelta d dt <.> ds` — a property checked in the testsuite.

### AST processing pipeline

- `Core/AstVectorize.hs` — BOT (bulk-operation transformation): eliminates `build1`/indexing-under-build, which would otherwise explode delta expressions.
- `Core/AstSimplify.hs` — smart constructors that simplify by inspecting term roots; `Core/AstTraverse.hs` — full bottom-up simplification passes; `Core/AstInline.hs` — inlining and global sharing elimination; orchestrated by `Core/AstEngine.hs` (`simplifyArtifactRev`, etc.).
- `Core/AstInterpret.hs` + `Core/AstEnv.hs` — interpret AST terms in any tensor-class instance (the backend).
- `Core/PPEngine.hs`, `Core/PPTools.hs` — pretty-printing of ASTs/artifacts.

A deliberate layering rule (`Core/Ast.hs:11-19`, copied into `Core/Ops.hs`): `Ast*` modules (syntax) and `Ops*`/`Carriers*` modules (semantics) are kept largely apart, the principal crossings being `AstInterpret`/`AstEnv` (syntax → semantics) and `OpsAst`/`CarriersAst` (semantics built from syntax). The source says *rarely*, not *only*, and means it: `AstSimplify` and `AstTraverse` also import `Core.Ops` and `CarriersConcrete` to fold concrete values, `AstSimplify` additionally pulling named helpers from `CarriersAst`, and `AstMethodLet`/`AstMethodShare` import `CarriersAst` and `OpsConcrete ()`, the latter for instances alone, with `AstMethodShare` adding `CarriersConcrete`. Six `Ast*` modules cross, not two — a tendency with named principal crossings, not an invariant to reason from.

### Supporting pieces

- `Core/Adaptor.hs` — `AdaptableTarget` converts user-level collections (tuples, lists of tensors) to/from a single tensor-kind representation `X vals`; this is how `grad` accepts functions over tuples.
- `Core/Unwind.hs` (and its more precisely-typed copy `Core/UnwindNum.hs`) — generic operations over nested product tensor kinds.
- `HordeAd.OpsTensor{,Ranked,Shaped,Mixed}` — the user-facing operation surface re-exported by the top-level `HordeAd` module; `Core/Ops.hs` holds the rawer class methods.
- `External/` — optimizers (SGD, Adam) and common NN building blocks.
- `example/` (public sublibrary `exampleLibrary`) — MNIST neural nets used by tests and benchmarks.

## Performance model

Runtime performance is an emergent property of four layers — AST term rewriting, the interpreter and its concrete kernels, GHC's optimizer, and the CPU — so it is decided empirically, not by reading source; a cost-centre profile is cheap to obtain (`--enable-profiling --profiling-detail=late` reuses the -O1 dependency store and rebuilds only the local packages). `contractAst` in `Core/AstTraverse.hs` (the backend-recognition pass, run just before interpretation) is by its own docstring "defined in an ad-hoc way based on benchmarks" (`Core/AstTraverse.hs:298`); treat any rewrite-rule change there as benchmark-gated.

Rules that keep the measurements honest:

- **Only criterion numbers belong in comparison tables and in performance reasoning.** A tasty "Bench" total (the `TestConvQuickCheck` poor man's benchmarks: wall-clock / 100 runs, including per-run random generation and `allClose`, on a coarse ~10ms timer) and a criterion per-call number are *different quantities*; never put both in one table, row or column. Treat any non-criterion figure — a GitHub issue's numbers, tasty totals (which are also machine/context/GC-dependent and not portable across setups or time) — as *anecdotal*: mention it as such, don't base a conclusion on it.
- **Criterion's "variance introduced by outliers" line is not a symptom to chase.** Criterion 1.6.5.0's `outlierVariance` derives it analytically from the mean, the stddev and the *number of samples* — never from any outlying measurement — and it saturates at (n-1)/n, so collecting more samples *raises* it: on `inp-192x192/S-exec-raw` it read 94.2% at 19 samples and 96.3% at 58, while the estimate itself converged. Read the R² printed under the `time` line instead. A severe verdict at R² above 0.99 means a benchmark with a warm-up ramp, which is every millisecond-scale benchmark in `convVjpBench`, not a broken measurement; what the ramp does spoil is the `mean`, which is why the property checker reads the slope.
- **For a per-call cost you doubt, difference two fixed-iteration runs.** `-n 200` minus `-n 100` (criterion's `--iters`, each in a fresh process), over 100, is a ground truth owing nothing to criterion's sampling or analysis, and wall and user time agree on it. On `inp-192x192/S-exec-raw` it gives 21.9ms where a default-budget report claims 18.6ms on its `time` line and 28.8ms on its `mean` — so reach for it before believing either, and before crediting an engine change with a shift.
- **Attribute a performance difference by controlled experiment, not hypothesis.** A ~3.3x gap between conv-gradient benchmarks, blamed in turn on harness noise and machine/GHC differences, was really a per-call artifact rebuild — settled by a discriminating benchmark (artifact hoisted out of the timed loop vs rebuilt per call); rule out machine/GHC only once the setup is confirmed identical. Before a number enters a commit message or public doc, ask what *instrument* produced it and whether a cheaper decisive check (printed-AST churn location, a provably-unaffected control) settles the question first.
- **The printed-AST tests are a free, decisive oracle for "can this rewrite affect that program at all".** An unchanged printed artifact means a byte-identical artifact and hence identical interpretation, so checking *where* a rewrite's printed-AST churn falls, before benchmarking, can settle a claim in minutes — a purported MNIST speedup was disproved this way (the churn was confined to CNN tests, so FC-MNIST could not have moved).

The procedural rules these imply once you are actually writing a benchmark — interleaving an A/B across two builds, choosing per-pair controls, pinning the benchmark selection across compared runs, using random rather than broadcast-constant inputs — are in `bench/CLAUDE.md`.

Cost facts worth knowing before optimizing — which operations dominate and why, what is metadata-only, the two pipelines' cost shapes, the gather/scatter cost model with its refuted redesigns, and how to add a `contractAst` rewrite rule — are in `.claude/rules/performance-model.md`, which a session loads when it touches an AST-processing module, `Core/OpsConcrete.hs` or anything under `bench/` — but the load is not dependable and a human gets no automatic load at all, so open it before optimizing anything or pricing a design against these kernels.

## Coding style

Author-generic style conventions are collected in the portable-notes section at the end of this file; what follows is horde-ad-specific.

- `StrictData` is on, plus `TypeFamilies`, `PatternSynonyms`, etc. — see `common options` in the cabal file. Type-level shape arithmetic relies on the `ghc-typelits-knownnat` and `ghc-typelits-natnormalise` plugins. `tools/bang-lazy-check.py` flags a bang that another equation of the same definition leaves unforced — run its `--selftest` first, and read the candidates it prints as input for its docstring's reading rules, not as confirmed defects.
- **Float epsilon margins depend on magnitude, GHC version and machine.** When compared values are large (e.g. gradients reaching ~5e5, where one Float ulp is ~0.03), widen the `assertEqualUpToEpsilon` margin rather than pinning exact low ulps or rewriting the expected values to one machine's output.

## Testing and correctness

- **Benchmarks are not correctness tests.** A body that forces a result by comparing it to itself (`allClose v v`) checks only that the body compiles — it never catches a wrong-operator or copy-paste bug — so when cloning a variant, cross-check every analogous position by hand: the operator called, the data helper used, the point at which a derivative artifact is interpreted. Every benchmarked path needs a *separate* `assertEqualUpToEpsilon` check on same-shaped data — hence deterministic correctness in `TestConvCorrect` alongside the poor man's benchmarks in `TestConvQuickCheck` — though existing tests of closely similar code suffice (the `cnn-*` benchmark groups lean on the many CNN tests).

How to keep that separation in practice — which module holds the QuickCheck properties and which the deterministic cases, how to refresh printed-AST expectations after a simplifier change, and how `cnnObjective` is shared with `convVjpBench` — is in `test/CLAUDE.md`, which a session loads automatically when working under `test/`; a human must open it there.

## Gotchas

- An unoptimized timing is ~8x slower than an optimized one and **not** comparable to it. The dev config sets `optimization: False`, so a mysterious ~8x discrepancy is usually exactly this and nothing subtler; the Tests section above says how to pass `--enable-optimization`.
- A build may not be using the sibling checkouts at all: the `packages: ../ox-arrays` line in `cabal.project.local` is often commented out, in which case the released ox-arrays from the cabal store is what gets built — check before assuming a local edit takes effect.
- The `Ast*`/`Ops*` layering rule is a tendency, not an invariant: its source (`Core/Ast.hs:11-19`) says *rarely*, not *only*, and six `Ast*` modules cross it against the two named as the principal crossings. The AST-processing-pipeline section above names all six; don't reason from the rule as though it held.
- Analogous-variant families run through the whole library — `Core/Unwind.hs` beside its more precisely-typed copy `Core/UnwindNum.hs`, the ranked/shaped/mixed operation surfaces, the per-carrier `Ops*`/`Carriers*` instances. Diffing analogous positions is how bugs surface here, and a property checked in one member is not checked for the family; this is the prime local instance of the repo-wide-grep rule in the portable notes below.

## Portable notes: same author, same machine

Nothing in this section is horde-ad-specific: it should hold for other projects by the same author, in the same coding style, developed on the same machine behind the same outer sandbox. A sibling checkout worked on from a session rooted here is inside that scope even when the sibling is another maintainer's repo — the machine did not change, and the patch is still authored here; only the coding-style specifics yield, to the style apparent in the file being edited, as those rules themselves prescribe. Examples are from horde-ad unless attributed.

### Coding style

- Haddocks are expected on all module headers and on functions/types in "major"/interface modules. Minor internal helpers get no haddocks; their comments, if any, must not be haddocks and may describe implementation details and go out of date — don't treat every comment as authoritative documentation.
- Prefer assertions over comments to document invariants, unless that would be too verbose.
- `-fno-ignore-asserts` stays on in the cabal `common options` stanza, so failed `assert`s crash release builds too — crash reports from released code can name assertions.
- Lens libraries are deliberately avoided; state lives in plain records (with record punning).
- GHC2024 is the default language; each project's default-extensions live in the cabal `common options` stanza. Projects normally set `StrictData` — assume it unless the project's notes say otherwise.
- Formatting: 2-space indent, 80 columns, spaces not tabs, spurious whitespace avoided, spaces around arithmetic operators encouraged. Inline comments (`--`) are prefixed with exactly two spaces, unless indented to match other comments. Operators such as `(` and `,`, `<$>` and `<*>`, comment starts, etc. on consecutive lines either align or, if that would make lines too long, indent by 2 spaces from the previous indentation level. Generally, relax and stick to the style apparent in the file being edited.
- Put large, mechanical formatting changes in their own commit, separate from substantive changes.
- If hlint is still too naggy, adding more exceptions to `.hlint.yaml` is fine — don't contort code to appease it.
- **Uniformity across analogous positions is itself a review tool.** Parallel code (e.g. the `Preserving`/`Shrinking`/`Padded` × `dKrn`/`dInp` × size families in the conv tests) and its comments should be identical modulo names and shapes; diffing analogous positions is how bugs surface, and a drifted one is normalized toward the cleaner form, not the first draft. One level up, things meant to be compared (benchmark variants, test cases) are designed as one-to-one counterparts — measuring the same stage, differing only along the compared axis, adjacent in the output — not accreted one probe at a time.
- **Order definitions as they are used, and let every summary span its whole subject.** Auxiliary definitions, do-bindings, list entries and top-level functions follow the order in which their consumers run, print or assert, wherever that order is deliberate or visible; an overview (module haddock, section comment) covers every member of what it describes, not the subset that existed when it was written. Both properties decay silently under accretion — after adding to a set, re-normalize the whole set, not just the new member.
- **One meaning per name, and label deliberate asymmetries.** A letter or abbreviation keeps a single meaning per vocabulary (not `S`/`H` as both the pipelines and the gather orientations they produce, nor `c` as both concrete and contracted); and where uniformity is intentionally broken — a counterpart deliberately absent, a definition that is a fixture rather than a candidate — the site says so and why: an unexplained asymmetry reads as drift and costs a review round-trip.
- **Comments.** A substantial note that sibling sites would repeat with only names changed is stated once, at its canonical occurrence; tiny notes, by contrast, are repeated identically at every analogous position. Match the codebase's spelling and hyphenation (e.g. "poor man's", not "poor-man's") and keep terminal punctuation consistent across parallel clauses (don't end one with ";" and its sibling with "."). A comment must still match the code after refactors — watch for notes invalidated by later changes. Leave pre-existing comments alone unless asked — flag them instead.
- In tests, an expected crash may never fire due to laziness: an assertion or lookup error is swallowed if the offending value is never forced — so force it, and under `StrictData` forcing to WHNF is enough, a strict constructor's fields being forced with it, which here means WHNF fully builds an AST. Catch real assert failures with `Control.Exception.try`, rather than pattern-matching on output; the `blame`/`swith` details (from the `assert-failure` package) go to the trace output, not into the exception.
- **Prove a self-checking assertion is non-vacuous.** An invariant check — e.g. verifying that scatter is the adjoint of gather via `sdot0 (sgather x f) y == sdot0 x (sscatter y f)` — should be shown to actually fail when the property is deliberately broken, or it may be passing vacuously.
- Share the objective between a test and its benchmark via one exported helper, parameterized by what differs, so the benchmark provably measures what the test validates — share code, not configuration.

### Working style

- **Scope discipline.** On an ambiguous request ("the *new* tests") take the narrower reading, do it, and flag the boundary with an offer to expand — don't silently touch pre-existing code. Split unrelated work into separate PRs (e.g. convolution benchmarks + tests in one PR, the simplifier fix in another).
- **Verify before claiming done.** "Uniform" / "correct" / "passes" must rest on an actual line-by-line cross-check or a test run, not on the fact that it compiled; a claim about a touched file covers its pre-existing code too, so audit that as well.
- **Only/every/never claims must rest on repo-wide grep, not on the file where the pattern was first noticed** — analogous-variant families (`Preserving`/`Shrinking`/`Padded` × `dKrn`/`dInp`, the ranked/shaped/mixed op surfaces, the `Ops*` instances) make single-file generalization treacherous. The same discipline applies before concluding "this cannot happen here": grep for *every* site that could do it. Over prose rather than code, grep the unwrapped form — `wrap80 --unwrap DOC` — or the search is only as complete as the line breaks allow: a phrase the pattern needs whole stops matching the moment a wrap falls inside it, and the silence reads the same either way. That is not hypothetical here; it cost `tools/check-doc-refs.py` two of README's backticked references, which is why that checker now reads the unwrapped form too.
- **Classify by the property you need, not by the proxy that greps easily.** Building LambdaHack's leader-conversion inventory, functions were bucketed by whether their *own* body performs an interactive wait — mechanical, and wrong for the one whose wait sits in a helper it calls (`closeDirHuman`, whose `pickPoint` waits for it), which landed in the "harmless" bucket until re-read. The proxy is fine as a first cut if the write-up says which property it actually tested and treats its own count as a floor; a fixture or a plan that rests on the proxy silently inherits its blind spot, the same way misreading a three-disjunct predicate as two produced a fixture whose code path never fired.
- **A citation that resolves can still lie.** A `file:line` reference survives a refactor that moves the line: the file is long enough, so the check passes and the reference now points at whatever slid into that slot (in LambdaHack, a `CliMock` citation came to name a comment two hundred lines away). That is why the citation checker prints the snippet it found rather than only a verdict, why a document's verification stamp asserts the *reading* and not merely the resolution, and why the stamp names the newest commit touching a cited file — the event that can invalidate the reading is exactly that file moving. The same holds at the HTTP level, where nothing here checks it at all: a URL answering 200 is not evidence that what the sentence attributes to it is still there — CREDITS.md's MNIST provenance link now serves an empty directory index, all four named files gone, at the same 200 it always gave — and the checkers fetch nothing, `URL_RE` matching only pinned `blob/<sha>/` permalinks and settling those against the commit rather than the network.
- **Prove a search non-vacuous before trusting its silence.** A grep that finds nothing has proved nothing until it is known to find something: run it first against a case known to be present. Two wrong answers in one session came of skipping that (in LambdaHack: `grep '^??'` over colourised `git status` output, the git notes below, and concluding a note was absent from every document after grepping one of its phrasings). It is the rule already stated for assertions and for checkers, applied to searches — and it reaches further than greps: a checker branch with no live control in this repo is a silent search too, which is why the tools under `tools/` name the branches their own recipes cannot exercise here. So is reading a file out of an archive: `tar xzOf PKG.tar.gz DIR/File.hs | grep -c NAME` prints 0 just as readily for a mistyped in-archive path as for an absent name, so grep something known to be in that file first — this is how the orthotope version pin in `.claude/rules/performance-model.md` was established rather than guessed.
- **Commits should be clean and logical, not a diary of the work.** File-partition them, order them so exports precede uses, and fold a follow-up refactor into the commit where the code is logically born rather than adding "add then move" churn.
- **Never push, or open/force-update a PR, without an explicit go-ahead.** Permission to make a change is not permission to publish it.
- **Drafting GitHub-bound texts.**
  - One file per destination (issue, its design comment, PR description, upstream PR), staged in `docs/`, posted or not.
  - Keep the *design* implementation-ignorant and put measured results in the PR description.
  - Deliberate overlap between files is fine, to make each self-contained.
  - Don't attribute design intent to code that is merely generic ("assumes irregular indexing") — state observed granularity and cost, not motives.
  - Prefer reference-style markdown links to keep the prose readable.
  - Wrapping is per destination: GitHub renders single newlines as hard `<br>` in issue/PR/comment *bodies* (though not in rendered `.md` files), so a draft meant to be pasted into an issue body, PR description or comment is kept *unwrapped* — one long line per paragraph (blank line between paragraphs; tables, code fences, list items, reference-link definitions and `Co-Authored-By` trailers each still on their own line) — so the browser soft-wraps it, and it is never re-wrapped to 80 columns; a doc read as a repo file (e.g. README, committed notes) keeps that file's normal wrapping instead.
- **Links that cite source code — in GitHub-bound texts and the reference documents — must be GitHub permalinks pinned to a commit hash that is on `master`** (`…blob/<commit>/….hs#L12-L34`): branch-name and unpinned links drift or die when branches move, while a master hash survives rebases and stays verifiable — the citation checker validates such permalinks against the pinned commit and then requires that commit to be an ancestor of `origin/master`, since `git show` resolves an unpushed or squashed-away commit from the local object database just as readily, and such a link 404s for everyone else. Deliberately-living whole-file links (e.g. the README's `blob/master` pointers) are outside the rule, as are links to foreign repos, which the checker cannot verify.
- **State mathematical properties in the code's surface notation, not abstract math** (in docs and comments alike). Write the gather/scatter adjoint law as `sdot0 (sgather x f) y == sdot0 x (sscatter y f)`, not `⟨gather x, y⟩ = ⟨x, scatter y⟩`: keep the index function `f` explicit rather than hidden in the operator name, and put quantifiers first (*for all `f`, `x`, `y`*). It reads in the vocabulary of the code and keeps the shapes checkable.

### Sandboxing on the dev machine (outer wrapper + inner sandbox)

Claude Code sessions on Mikolaj's machine run inside an outer bwrap sandbox wrapper (PID 1 is `bwrap`), beyond Claude Code's own (inner) sandbox. Current state and its implications:

- Run `git` writes, `cabal` and `gpg` unsandboxed — the inner sandbox mounts `.git/config`, `~/.cabal` and `~/.gnupg` read-only. `git checkout -b` / `branch -f` fail to lock the config, though the ref often moves anyway — verify refs afterwards. GPG signing (`commit.gpgsign` is on) fails sandboxed and works unsandboxed, so never fall back to `--no-gpg-sign`; SSH pushes likewise work only unsandboxed.
- **Anything outside the working directory refuses a *sandboxed* Bash write and accepts an unsandboxed one**, the read-only HOME mounts and the sibling checkouts alike: `~/.claude/projects` and `../orthotope` were measured in all four cells and do not differ, whatever a mechanism story suggests. The Write and Edit tools reach both regardless. So there are always two routes, and the choice is worth real tokens: Edit for a few lines, an unsandboxed `python3` splice for anything structural, a move otherwise shipping the block twice through Edit and costing tens of thousands of tokens where a script costs hundreds. Expect the wrong half to be learned by accident — a session meeting `Read-only file system` from a *sandboxed* script concludes Bash cannot write there at all and reaches for Edit ever after.
- **A blocked write leaves the command's fate unreadable from the shell's output.** Measured both ways: a simple command's redirections are checked before exec, so `cmd > blocked.log &` and `nohup cmd > blocked.log &` report the failure and run nothing at all, while a pipeline fails only at its consumer, so `cmd | tee blocked.log &` reports the same error and `cmd` detaches and keeps going. The log is missing either way, so the launch reads as never having happened — two copies of a benchmark once ran side by side, contending, because one was read that way. Confirm a launch by counting the processes unsandboxed, not by the launching shell's output.
- Paths the wrapper blocks report "No such file or directory", not "Permission denied". If a path outside the repo seems missing — especially one documented as expected, like the `../ox-arrays` sibling checkout — suspect the wrapper rather than recording the path as absent. `dangerouslyDisableSandbox` bypasses only the inner sandbox, never the wrapper. `tools/check-doc-refs.py` encodes the same rule: it resolves sibling checkouts when present and *stops* (exit 2) when one is not, rather than falling back to a weaker check, so a BLOCKED run means the check did not happen, not that it passed.
- **Where a sibling checkout and the released version it tracks disagree, the checkout wins.** It is ahead of the release and actively worked on, not stale, so read it for what upstream *is*: `../orthotope` sat at 0.1.8.0 plus unreleased commits rewriting the very strided fallback the gather cost bullet in `.claude/rules/performance-model.md` describes, which would have been recorded as current had the release been treated as the authority. The cabal store answers the two questions the checkout cannot: what to read when the wrapper hides the mount, and whether a *version-sensitive name* a document pins is really in the release the build plan resolves. A note resting on upstream code the checkout has since changed says so, and names what to re-measure when that work lands.
- The wrapper mounts a fixed set of HOME paths, curated per-path rather than per-directory, plus whatever repo checkouts it was launched with, skipping in silence any that do not exist — which is where the previous bullet's "No such file or directory" comes from. The fixed part can be relied on; the checkouts are what varies from session to session, `~/r` having at times held only the current repo, so verify a sibling at the moment it matters rather than inferring it from habit. That an entry is visible still says nothing about how much of its contents is: `~/.ssh` carries public material only.
- Sandboxed `git status`/`ls` show phantom untracked dotfiles in the working directory that don't exist on the real filesystem. HOME is *not* remapped to the repo root, whatever the names suggest: the inner sandbox bind-mounts `/dev/null` over eleven names in the directory it was launched in, once per Bash call. So one path stats three ways — a character device 1,3 mode 666 from inside the call holding the mount, a regular empty file mode 444 (the placeholder that mount needs) from any other mount namespace while that call is live, whether an unsandboxed command or a second concurrent sandboxed one, and absent when no call is running. The form follows vantage and timing, not the checkout, and a sibling checkout gets none of them at all — which is the half measured from here, this repo having been the sibling when the three states were established. A session rooted here is the one that can confirm the device state; the mode-444 reading this file used to carry is what the account predicts a second concurrent call, or an unsandboxed one, would see. Ignore them; verify with an unsandboxed command before deleting any. The eleven are `.bashrc`, `.gitconfig`, `.gitmodules`, `.mcp.json`, `.profile`, `.bash_profile`, `.zshrc`, `.zprofile`, `.ripgreprc`, `.idea`, `.vscode`, worth listing because two of them are names a repository could legitimately carry and would then read as empty rather than missing. That is enough to move a checker's verdict: a backticked `.mcp.json` in this file makes `tools/check-doc-refs.py` resolve it from a session rooted here and fail it from one where this repo is a sibling, or from an unsandboxed run, until an entry in `tools/doc-refs-allow.txt` settles the answer everywhere. The same masking covers the `.claude/` entries a session must not write, settings.json among them though the checkout carries none, and there it reaches Claude Code itself: its `--debug` log records a *Detected change to* that path and reloads every settings source on it — CA certificates re-read, the sandbox configuration re-derived, all permission rules replaced. That is inert only because there is nothing to replace: `permissions` is empty in the user settings and in `.claude/settings.local.json`, and no project `sandbox` block competes with the user-level one carrying `enableWeakerNestedSandbox`. Adding either gives the reload something to lose. The same reload reads `.mcp.json` at length zero and logs it as invalid JSON, which costs nothing while no such file exists — but a real one here would load at startup and then read as empty on the first reload after any Bash call, dropping its servers mid-session.
- The inner sandbox is in its own PID namespace, so `ps` there lists only the session's own processes and `kill -0 <pid>` is not a liveness test: it fails for a process that is running fine, and an `until ! kill -0 …` waiter therefore returns at once. That reported a still-running build as finished once. Poll unsandboxed, or watch the thing's output file rather than its pid — except that a file whose creation the sandbox blocked stays absent whether or not the process is running (sandboxing notes above), so there its absence proves nothing and only the unsandboxed process list settles it.
- System state under wrapper-hidden paths cannot be inspected from inside a session; such diagnosis must be done by Mikolaj in a plain terminal. Most of `/etc` is in that class, the wrapper carrying `resolv.conf`, `hosts`, `ssl`, `passwd`, `group`, `alternatives` and `fonts` and no more, so `/etc/apparmor.d` here is an instance of one rule rather than a separate surprise, and the next `/etc` path to come back missing is predictable. The last two were added on 2026-08-10 after a session traced failures to them, `/etc/alternatives` being what the shell-tooling notes below rest on.
- The nested inner sandbox works only because three things hold; if sandboxed commands start failing at startup, check these first:
  - the Ubuntu AppArmor userns restriction is off (`kernel.apparmor_restrict_unprivileged_userns=0`, no `bwrap-userns-restrict` profile);
  - the wrapper mounts the repo read-write;
  - `enableWeakerNestedSandbox: true` is in effect — inherited from the `sandbox` block of the user-level `~/.claude/settings.json` (a project `sandbox` block wholesale replaces the user-level one — settings objects don't deep-merge — so a project that defines one must repeat the flag).

### Git and GitHub in sessions

- `gh` is authenticated only unsandboxed, and sandboxed it degrades rather than fails, which is the trap: its real token is in the keyring, out of the inner sandbox's reach, so it falls back to the read-only `~/.config/gh/hosts.yml`, whose token is invalid, and proceeds unauthenticated. Measured both ways — 60 requests an hour against 5000, and `/actions/jobs/<id>/logs` answering 403 "Must have admin rights to Repository" where an unsandboxed run returns the log. The network itself is there sandboxed, a plain `curl` to api.github.com giving 200, so what is missing is the credential and not the route, and `gh auth status` names it outright. Run `gh` unsandboxed, alongside `git` writes, `cabal` and `gpg`.
- `git status --short` is colourised even through a pipe — the bytes are `^[[31m??^[[m path` — so `grep '^??'` silently matches nothing. Use `git status --porcelain`, which is defined as machine-readable and is never colourised.
- A `git stash pop` chained after a `git stash push -- <path>` is a trap, because the push can succeed having saved nothing: given a pathspec with no local changes it prints "No local changes to save" and exits 0, so the pop then takes the *top of the stash stack* — hundreds deep here, holding parked branch work — restores that into the tree and drops the entry. Park a file by copying it aside, not by stashing it.
- Interactive git is unavailable (tool commands run without a TTY, so editor and prompt loops hang): no `rebase -i`, no `add -i`. Rewrite history with `git reset --mixed <base>` + re-`add`/`commit` per file group, reusing messages via `git commit -C <hash>` / `-F <file>`.
- Amending a non-HEAD commit (no `rebase -i`): save working-tree edits as a patch, `git reset --hard <target>` (spares untracked files), apply, `--amend`, then `git cherry-pick` the successors (conflict-free when they don't touch the amended files); update recorded hashes.
- The repo root accumulates many untracked scratch files (`log*`, `*.prof`, `cabal.project.local.bkp*`, `.emacs.desktop*`, etc.); leave them alone and never `git add` them wholesale.

### Build and shell tooling in sessions

- `pkill -f PATTERN` matches the issuing shell's own command line, which contains the pattern, so it kills the shell that ran it — the tool call comes back with exit 144 and nothing else, twice mistaken here for the command failing. Take pids from `ps` and `kill` those instead. Sandboxed calls are spared that, by accident rather than by design: Claude Code's shell snapshot shadows `pkill` with a function that refuses any pattern whose `pgrep` hit equals `$CLAUDE_PID`, and in the inner sandbox's PID namespace the issuing shell is itself PID 2 — the number the CLI holds in the wrapper's namespace — so what fires is a collision between two namespaces rather than recognition of the CLI. Don't lean on it: unsandboxed, where the shell carries some other number, the same command still killed its own shell at exit 144. `pgrep -f` self-matches identically and, being shadowed by nothing, fails more quietly: an `until ! pgrep -f PATTERN` waiter finds its own shell, so the condition never goes false and it waits until something kills it — where `pkill` at least ends the call loudly. A pattern the matcher cannot match, `'seq 1 [6]0'`, dodges both — but only its own occurrence: a kill-then-relaunch script still dies through the literal name in its later launch line, measured in LambdaHack at exit 144 unsandboxed and meeting the refusal above when sandboxed, so kill and relaunch go in separate calls.
- Commands managed by `update-alternatives` — `awk`, `cc`, `which`, `vi`, `pager` and the rest — resolve in sessions since the wrapper began mounting `/etc/alternatives` (2026-08-10); before that every `/usr/bin` symlink pointing there dangled. The fix is that one mount and not a shim per command: the `~/.local/bin/awk → mawk` link that had stood in for one of them is removed, and a retargeted alternative now reaches a session on its own. `hlint` and `stylish-haskell` are on PATH (via `~/.cabal/bin`) and work in-session, sandboxed included.
- `grep` is not the binary on PATH but a bash function Claude Code writes into its shell snapshot, routing to a ugrep (7.5.0) embedded in the `claude` executable; `find` is shadowed the same way, by bfs. A function shadows every PATH entry and `\grep` does not escape one, backslash suppressing aliases rather than functions, so `command grep` — GNU grep, at `/usr/bin/grep` — is the way back; the shims are not exported, so a Makefile recipe or a `python3` subprocess already gets the real thing. Three of the differences are silent: a recursive search skips gitignored paths, `--ignore-files` being injected, so a walk over the repo passes over `log*`, `dist-newstyle` and `*.prof`; binary files are skipped (`-I`), so `-c` prints nothing and exits 1 where GNU prints a count and exits 0; and `-r` output paths lose their leading `./`. The regex dialect is *not* one of them — GNU BRE's `\|` and its siblings behave identically — so an alternation that matches nothing means `-E`, `-P` or `rg`, where `\|` is a literal pipe in any grep; blaming that on ugrep put a fabricated machine fact one approval away from this file. What is ugrep's own: `-P` means PCRE2, it can reject a regex outright with `exceeds complexity limits` where GNU grep would run it, and on the one-line-per-paragraph documents here a bounded-repeat alternation can instead run for minutes — reach for python when a pattern gets involved. The checkers under `tools/` are unaffected: they match with Python `re` rather than with whatever `grep` resolves to. Only `check-doc-refs.py` shells out to `git grep` at all, and only for its flag-usage check.
- To combine several tasty `-p` patterns, tasty wants awk-style syntax: `-p "/foo/ || /bar/"`.
- A tasty `-p` pattern matches by *containment* and cannot be anchored, in two forms that fail differently. A pattern of nothing but alphanumerics, `.`, `_`, `-` and spaces is taken whole as a literal substring and never parsed — the ordinary form, `-p "4S"` — while anything else goes to the awk grammar, where an ERE token `/foo/` recognizes no special characters either and `$NF` is the test's own name. So an anchor fails two ways and only one is loud: `-p "^detSquare"` is rejected, "is not a valid pattern", where `-p "/^detSquare/"` is accepted and silently selects nothing. `-p '$NF == "detSquare9"'` is the exact-match form. The consequence is silent, and biting wherever names are numbered: `-p "gatherNested1"` selects two tests, `gatherNested1` together with `gatherNested12` — so a filter believed to name one test quietly runs two, and a count taken through it moves for reasons nobody sees. Mint a marker by listing before the series exists: the same `--list-tests` reports a count for a marker that does exist, which is what keeps the check from passing vacuously.
- Criterion (the benchmark suites) filters differently and does *not* accept that syntax — it has no `-p`: bare positional args are **prefix** patterns on the full `group/bench` path, and `-m glob`/`-m pattern`/`-m ipattern` switch the match mode (e.g. `--benchmark-options='-m glob "*/S-exec"'` to pick a bench across groups, or a bare `--benchmark-options='cnn-24x24'` prefix).
- **A verification command must not be piped.** A shell pipeline exits with its *last* command's status, so `cabal test CAFlessTest --enable-optimization | tail -40` reports `tail`'s success whatever the run did — and the session harness then reports "exit code 0", which reads exactly like a pass. Redirect to a file and echo `$?` instead. It bites harder here than in most places: warnings are deliberately ignored (Standing checks above), so the exit status is the whole signal and the pipe is precisely what discards it. The failure is silent by construction and survives every other check, which is why it belongs here rather than in one tool's recipe — `tools/check-plan-citations.py`'s non-vacuity recipe already tells its own reader to check the status without a pipe, having once read five successes that were four refusals.
- GHC emits warnings only on *recompilation*: a cached, up-to-date build can hide warnings (e.g. `-Wredundant-constraints`) that a full rebuild would surface — don't infer "no warnings" from a clean second build. Optimization level hides a second class: `-Wmissed-specialisations` fires only when the specialiser runs, so a from-scratch `-O0` build reports none of it, and `--ghc-options=-fforce-recomp` does not help — cabal answers "Up to date" and compiles nothing, since the flag doesn't reach its staleness check. To force a genuine rebuild, build into a fresh `--builddir`, which leaves the existing artifacts alone — then delete it, because hlint's built-in ignores cover `dist` and `dist-newstyle` but no other name, and hlint does not read `.gitignore`, whose `dist-*` would otherwise have covered it: a `--builddir=dist-seq` left in place put cabal's unpacked ox-arrays sources under `hlint .` and turned `No hints` into 28.
- **A binary under `dist-newstyle` can silently predate the tree, so check before measuring it.** `cabal build convVjpBench --dry-run` names what it would rebuild and why ("file X changed"), which is the cheap way to know the executable about to be timed is the one the source describes. Reverting an edit without rebuilding cost two wrong conclusions in one session: the binary still carried the reverted code, and the extra startup work it did was read as a property of the suite, contradicting an earlier measurement that had been right all along.
- Keep one set of cabal flags across a session — changing flags (e.g. toggling `--enable-optimization` or `--enable-profiling`) forces a full rebuild of the local packages, though each flag set's dependency builds stay cached in the store. Pass such flags on the command line rather than editing `cabal.project.local`.
- The `/tmp` scratchpad is wiped by a machine restart, and the wrapper's tmpfs over `/tmp` also hides it from Mikolaj's own shell — put anything that must survive (patches, notes) or that he has to run or open himself (a `! bash foo.sh` script, a diff to review) in the repo tree instead, with a note to delete it afterwards; binaries just get rebuilt. Handing over a scratchpad path yields "this file doesn't exist" and a wasted round trip. `$TMPDIR` points there only under the inner sandbox; an unsandboxed command sees the variable unset, so `$TMPDIR/foo` expands to `/foo` and the write silently succeeds — spell scratch paths out in full whenever sandboxing is off.
- Exact dependency sources are always available: unpack `~/.cabal/packages/hackage.haskell.org/<pkg>/<ver>/` matching `dist-newstyle/cache/plan.json`.
- `.github/workflows/haskell-ci.yml` is generated by `haskell-ci` from the `.cabal` file — regenerate it (`haskell-ci regenerate`) rather than hand-editing. Anything the generator does not produce belongs in `cabal.haskell-ci`, not in the generated file: a plain field where one covers it (`apt:` for extra system packages, `run-tests:`, …), and `github-patches:` for a diff reapplied on every regeneration. A hand edit left outside that config is not merely fragile, it disappears *silently* on the next regenerate — which is what a rewritten `tests` step and a whole `benchmarks` step here were exposed to, a plain regenerate dropping both without a word, until the first moved into the patch and the second into a hand-written workflow of its own. After changing the config, regenerate twice and compare: a patch that applies cleanly once can double-apply. (In LambdaHack the same role is played by an `apt:` entry, `libsdl2-ttf-dev`, which that repo nearly lost the same way.)
- Toggle-based A/B builds: make a rule's guard unsatisfiable (e.g. `sigmaL /= sigmaL`), build and copy the binary aside, restore + rebuild + copy again, then run the two preserved binaries in interleaved pairs (no rebuild between A and B); an edited `Core` module rebuilds in ~10 min.
