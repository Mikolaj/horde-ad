# Test harness guidance (`test/`)

How to *invoke* the suites, and the `--enable-optimization` requirement that makes their timings comparable, are in the root `CLAUDE.md` — running `cabal test` from the repo root does not load this file, which arrives only when a session opens something under `test/`. What follows is for writing and reading the tests themselves.

File:line references were verified against the tree at commit `d282ed596` (2026-07-31); the citation pass proves a cited line exists — this stamp, that it still says what the claim around it needs.

## Layout

Test suites in `test/` are thin `Main` wrappers combining `testTrees` from modules in `test/simplified/` (the `testCommonLibrary` sublibrary); test tools (`EqEpsilon` for epsilon float comparison via the `--eq-epsilon` tasty option, `CrossTesting`, `Shared`) live in `test/tool/`. MNIST tests read gzipped IDX files from `samplesData/`. CAFlessTest must stay sequential: the AST-variable counter reset is not thread-safe, and some tests check printed ASTs whose numbering varies with execution order. One thing keeps it that way, and it is easy to undo without noticing: its whole tree is wrapped in tasty's `inOrderTestGroup` (`CAFlessTest.hs:33`), which plays tests in the exact order given — though tasty's own haddock warns that this holds only under the default test manager, so an ingredient such as tasty-rerun could ignore it. The suite also imports the cabal `exe-options` stanza rather than `exe-options-for-parallel-tests` (`horde-ad.cabal:126-145`), so it never receives `-N8`; that reads like a second, independent guard, and is not one. tasty takes its concurrency from `NumThreads`, which defaults to `getNumProcessors` and which `-N` does not touch (measured on GHC 9.12.4: `-N2`/`-N8`/`-N` moved `getNumCapabilities` to 2/8/16 while `getNumProcessors` stayed 16), and it then raises capabilities to match — only ever raising, so a smaller `-N`, or none at all, is overwritten. Measured: CAFlessTest, with no `-N` baked in, runs at `-N16` on this 16-core machine. `getNumProcessors` tracks the process CPU affinity mask rather than the machine — under `taskset -c 0,1` it reports 2 where `nproc` says 16 — so it is not "all cores" either. Without the ordering wrapper the tests would interleave, and on those 16 capabilities genuinely in parallel.

## Writing and maintaining tests

- **Deterministic vs QuickCheck split for stable timing.** Keep QuickCheck properties and poor man's benchmarks in one module (`TestConvQuickCheck`) and deterministic `testCase` correctness in another (`TestConvCorrect`), so the deterministic suite's wall-clock stays comparable across runs. Share helpers by *exporting* them from the QuickCheck module (no import cycle).
- **The printed-AST series runs as a unit, because every test that asserts on a printed AST carries `PP` in its name**: `cabal test CAFlessTest --enable-optimization --test-options='-p "/PP/"'`. Nothing outside that suite prints — the six modules that do (`TestAdaptorSimplified`, `TestConvSimplified`, `TestGatherSimplified`, `TestHighRankSimplified`, `TestMnistPP`, `TestRevFwdFold`) are all members of it — and the naming convention holds without exception: mapping every `testCase` to the helper it names turns up no print-asserting helper behind a name lacking `PP`. Keep it that way; a printed-AST test named otherwise leaves the series silently, and the refresh below then skips it until some later run fails on it. The filter is live rather than a no-op: it selects a proper subset of the suite, while a pattern naming nothing selects nothing. No count is quoted here because the command prints its own. The numbers inside a name are not filters, though, since `-p` matches by containment and cannot be anchored (the root `CLAUDE.md` has the rule): `-p "gatherSimpPP1"` runs `gatherSimpPP12` as well, and a bare `-p "PP1"` sweeps every `PP1`-containing name across the six modules. Name a single test with the `$NF ==` exact form, and mint a new marker by listing for it before the series exists.
- **Printed-AST regression churn** after simplifier changes is expected and mechanical: refresh the expected strings from a sequential `CAFlessTest` run (parse the tasty-hunit expected/but-got pairs; expect two or three rounds, since each test stops at its first failing assertion), keep that churn in its own commit, and watch for eps-based numeric tests (e.g. `3barS`) drifting in the last Float digit when operation order changes.
- **`cnnObjective` (exported from `TestMnistPP`, `TestMnistPP.hs:6`) is the objective shared between a printed-AST test and its benchmark**: `testCNNOPP2S` consumes it with a constant glyph at print-friendly sizes, `convVjpBench`'s `cnn-*` groups with a random glyph at square doubling sizes — the benchmark provably measures the net the test validates, and the refactor is verified free by the printed-AST test not churning.
