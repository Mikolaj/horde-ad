# Benchmark guidance (`bench/`)

Six criterion suites: five built over `bench/common/` (`BenchMnistTools`, `BenchProdTools`), and `convVjpBench`, which stands alone on `bench/ConvVjpBench.hs` over the test and example sublibraries. How to *invoke* them, which of them CI runs, and the rules for reasoning about the numbers afterwards are in the root `CLAUDE.md` --- running `cabal bench` from the repo root does not load this file, which arrives only when a session opens something under `bench/`. What follows is for writing and reading the benchmarks themselves.

The names cited here --- suites, criterion groups, cabal flags, functions --- and the one `file:line` citation were verified against the tree at commit `1a5aff556` (2026-08-14); the reference and citation passes prove a cited name or line exists --- this stamp, that each still says what the claim around it needs. The wording differs from the stamp in `CLAUDE.md` and in `test/CLAUDE.md` because this file mostly cites names, not lines.

## `convVjpBench`

The `convVjpBench` benchmark (`bench/ConvVjpBench.hs`; not built under the `release` flag) is the [#123](https://github.com/Mikolaj/horde-ad/issues/123) diagnostic: `conv2dPreservingS` gradient wrt kernel and wrt input (dKrn/dInp) sweeps at 6--192, the symbolic and handwritten pipelines decomposed into pairwise-comparable `S-*`/`H-*` stage variants, `gather48`/`scatter48` isolating micro-benchmarks, `cnn-*` groups timing a real shaped two-layer CNN gradient, and a `pitfalls` group with the suite's single recorder of each known measurement trap (artifact hoisting, constant-cotangent embedding).

Those concept names are not the criterion path, which trips up filtering: dKrn is the bare size groups (`6x6` … `192x192`, built by `benchesAt`) and dInp the `inp-*` ones (`benchesInpAt`), with the stage variants as the bench names under each --- so a run is picked out as `6x6/S-exec` or `-m glob "*/S-exec"`, never as `dKrn`, which appears in the source only as a comment and as the imported `conv2dPreserving_dKrn`. It uses only random data (`randomValue`), so it needs no `samplesData` and runs anywhere; `PRINT_TERMS=1` prints the compared gradient programs instead of benchmarking.

As the repo's only convolution-performance benchmark (the MNIST bench suites cover only FCNN nets) it outlives [#123](https://github.com/Mikolaj/horde-ad/issues/123): run it, with full criterion statistics, whenever touching conv-relevant code (gather/scatter rewrites in `contractAst`, the interpreter, the ox-arrays gather path) --- CI's per-push run is default-limit, so its time slopes land low and it checks only allocation (below). To analyze a run, collect it with `--benchmark-options='-L 30 --regress allocated:iters --json FILE +RTS -T'` and check the module haddock's numbered properties (`bench/ConvVjpBench.hs:96` --- deliberately this file's one line citation, which is what lets `--restamp` maintain the stamp above) with `python3 tools/check-conv-bench-props.py FILE`, which checks every one of them twice, against seconds per iteration to 10% and against bytes allocated per iteration to 5%; the haddock classifies whether a failure means a broken measurement, an engine regression, or a legitimately shifted cost model. Every option matters: the checker reads the per-iteration OLS slope criterion prints on its `time` line, which `--csv` does not carry (it holds only the mean, which the warm-up ramp inflates per benchmark); `--regress allocated:iters` and `+RTS -T` are what the allocation pass reads, and it looks that regression up unconditionally, so without them the checker exits on the first report in either mode; and the raised time limit is what leaves a millisecond-scale benchmark enough samples for that slope to converge --- at the default 5s it lands roughly 10--15% low. The checker gates on that itself, failing ahead of the properties on any slope fitted over too few samples or too poorly, so a collection that was too short says so rather than quietly shifting a property. What drives the raised limit is a handful of slow benchmarks, not the suite: at ~300ms per iteration the three `cnn-24x24` ones collect four to five samples at the default and fit at R² 0.918--0.989 --- the last of those above the R² gate, so only its sample count gives it away --- and `inp-192x192`, `192x192` and `cnn-12x12` are the next worst --- the gate names whichever fell short, so there is no list to keep. Those groups are also the only ones that *need* the long budget, though the checker's long-budget selection is wider: `gather48` and `scatter48` ride along so that the property comparing them is not fitted from one converged slope and one ramp-biased one. So the checker takes several JSON files and merges them, letting the slow groups run long and the rest run at the default for about 26 minutes against 54; its docstring holds the two selections, which have to partition the suite and must not cut across a property. Do not instead exclude the slow benchmarks from the checks: they carry 16 of the 84 property instances, every one of them at the sizes where gathers dominate and a rewrite can show up at all, so dropping them would leave a green run that verified nothing at scale.

The allocation half of that is what CI gates on, through `--allocation-only`: allocation is so nearly exact in the iteration count that even the four-sample `cnn-24x24` benchmarks fit it at R² 1.000000, so a default-limit collection gives an allocation verdict as good as an hour-long one, where the time slopes would need `-L 30`. `lint-and-test-suites.yml` therefore runs the whole suite that way on every push and checks the properties over allocation alone, which also leaves bytes allocated per iteration for every benchmark --- criterion prints it as the `iters` line under each `allocated:` block --- in a log GitHub keeps for ninety days, the point of printing them being to date a number that has started looking bad, nothing else here recording what allocation was months back. Those logs are a series only among themselves: CI resolves orthotope from Hackage where a local run may link the sibling checkout, so a CI number never compares with a local one, and a new orthotope release steps the whole series. What allocation cannot see is the standing caveat: the ~9--12× gather-against-scatter time gap is most of why the time properties exist --- a gap measured against orthotope 0.1.8.0, and since re-measured against the strided-fallback fix `.claude/rules/performance-model.md` records, which takes it to 2.55× in gather's natural orientation and 1.32× in its fastest --- the `bq-expand` form's figures, that form being the last candidate since 2026-08-22, when `mut-odo-vecdims` was decided as the implementation (orthotope's `micro-regime3/README.md`, the ceiling section), so they are re-measured when it lands. Which orthotope the sibling checkout is on therefore moves the two-gather chains severalfold, so record it with any number taken here --- that A/B covered `gather48` and `scatter48` only, where 4 of 13 benchmarks moved severalfold, 4 moved ~0.85× the other way at byte-identical allocation (the fused gathers --- a position effect of RTS pool state, `docs/position-effect.md`, not the fix; the same allocation test classifies the next one as real), one scatter moved 1.24× at 1.23× the allocation (`two-scatters-ad-shn-sorted`, the only scatter carrying compensating transposes and so the only one whose slice views reach this fallback), and 4 not at all. A conv group has since been measured on the same two builds: the dKrn sweep's `S-exec` runs 1.6× faster at `6x6` and 3.5--4.2× from `24x24` up, at 2.1--6.5× less allocation. Refuted, and not to be reopened without new evidence: moving the suite to tasty-bench --- its estimator resists the ramp better, being an origin-forced two-point fit that discards the small-iteration measurements and stops on precision rather than on a clock, but it keeps only two measurements and so could not have produced the per-sample evidence these rulings rest on, and every recorded number would need re-collecting; dropping the 192 groups, when the slowest benchmarks in the suite lie outside them, in `cnn-24x24`; and trimming variants within a size, which breaks the pairwise-comparability design and several of the properties, and in fact aborts the checker outright.

The `cnn-*` groups consume `cnnObjective`, the objective they share with a printed-AST test; the reasoning about that sharing, and about refreshing the test when the simplifier moves, is in `test/CLAUDE.md`, which a session loads when working under `test/`.

## Writing a benchmark

- **An A/B across two *builds* needs interleaving and controls, because recompilation itself moves numbers.** Two binaries differing by a one-line toggle shift *unaffected* benchmarks by ±2--5% (code-layout/codegen noise; the artifact can be larger and need not shrink with size --- the `NotShared` prod benches run measurably slower on a build carrying a rule their `cgrad` pipeline never reaches, and that gap *grows* with product length, ~4%/15%/22% at 100/1000/10000, the three sizes those benches exist at, a per-iteration placement effect rather than a fixed small-scale one; a dead-rule-guard rebuild returns toward baseline but only weakly corroborates, the compiler being free to drop the always-false guard), and batched runs (all A, then all B) additionally confound with time/thermal drift. Run interleaved A/B pairs (drift cancels within a pair) and include per-pair controls: a suite the change provably cannot affect (e.g. the concrete `VTA` MNIST groups of `BenchMnistTools` for a `contractAst` change --- the concrete pipeline never runs it), and/or a change-independent variant (e.g. `S-exec-raw` for a `contractAst` change: the raw artifact is contraction-independent --- see the `vjpArtifact` cost fact in `.claude/rules/performance-model.md` --- so it is identical across the toggle). The change's effect is the target's per-pair ratio minus the control's.
- **An A/B also needs the same benchmark selection in every run compared, and its decisive numbers taken one benchmark per process: a predecessor's leftover RTS pool state can shift a follower's time ~20%.** Interleaving and controls cannot catch it, both arms of a pair sharing their roster, and pinning alone is not sufficient when the compared builds change a predecessor's own allocation profile. Mechanism, evidence and the practical trade-offs are in `docs/position-effect.md`.
- **The nursery is `-A32m` by decision (2026-08-21, the root `CLAUDE.md`'s Tests section), not a knob to tune per ramp or per benchmark.** Expect `inp-192x192`'s `H-*` variants to promote there as they did at `-A64m`, where its uncontracted term exceeded the nursery and three of the four slowed 2.1--2.4x (GC 5--6% of wall against 0.02%), property 6 (`S-exec <= H-exec`) to pass spuriously, and the numbered time properties, recorded before the move, to want recalibrating on the first full run rather than reading as regressions; allocation per iteration does not move with the area, so the allocation properties CI gates stand. `-A1G`, the previous setting, lost on every axis measured --- `docs/speculative-todos.md` holds the evidence.
- **Benchmark inputs must be random, not broadcast constants.** A constant input like `treplicate … (sscalar 7)` is a stride-0 broadcast that the simplifier constant-folds *through* the very operations you mean to time --- a CNN gradient benchmark with a constant glyph lost its im2col gathers to folding and under-measured 24ms vs the honest 158ms. Use `randomValue`; a constant is only right when the *test* (e.g. a printed-AST test) wants a canonical small term.
