# Benchmark guidance (`bench/`)

Six criterion suites: five built over `bench/common/` (`BenchMnistTools`, `BenchProdTools`), and `convVjpBench`, which stands alone on `bench/ConvVjpBench.hs` over the test and example sublibraries. How to *invoke* them, which of them CI runs, and the rules for reasoning about the numbers afterwards are in the root `CLAUDE.md` --- running `cabal bench` from the repo root does not load this file, which arrives only when a session opens something under `bench/`. What follows is for writing and reading the benchmarks themselves.

The names cited here --- suites, criterion groups, cabal flags, functions --- and the one `file:line` citation were verified against the tree at commit `1a5aff556` (2026-08-14); the reference and citation passes prove a cited name or line exists --- this stamp, that each still says what the claim around it needs. The wording differs from the stamp in `CLAUDE.md` and in `test/CLAUDE.md` because this file mostly cites names, not lines.

## `convVjpBench`

The `convVjpBench` benchmark (`bench/ConvVjpBench.hs`; not built under the `release` flag) is the [#123](https://github.com/Mikolaj/horde-ad/issues/123) diagnostic: `conv2dPreservingS` gradient wrt kernel and wrt input (dKrn/dInp) sweeps at 6--192, the symbolic and handwritten pipelines decomposed into pairwise-comparable `S-*`/`H-*` stage variants, `gather48`/`scatter48` isolating micro-benchmarks, `cnn-*` groups timing a real shaped two-layer CNN gradient, and a `pitfalls` group with the suite's single recorder of each known measurement trap (artifact hoisting, constant-cotangent embedding).

Those concept names are not the criterion path, which trips up filtering: dKrn is the bare size groups (`6x6` ... `192x192`, built by `benchesAt`) and dInp the `inp-*` ones (`benchesInpAt`), with the stage variants as the bench names under each --- so a run is picked out as `6x6/S-exec` or `-m glob "*/S-exec"`, never as `dKrn`, which appears in the source only as a comment and as the imported `conv2dPreserving_dKrn`. It uses only random data (`randomValue`), so it needs no `samplesData` and runs anywhere; `PRINT_TERMS=1` prints the compared gradient programs instead of benchmarking.

As the repo's only convolution-performance benchmark (the MNIST bench suites cover only FCNN nets) it outlives [#123](https://github.com/Mikolaj/horde-ad/issues/123): run it, with full criterion statistics, whenever touching conv-relevant code (gather/scatter rewrites in `contractAst`, the interpreter, the ox-arrays gather path) --- CI's per-push run is default-limit, so its time slopes land low and it checks only allocation (below). To analyze a run, collect it with `--benchmark-options='-L 90 --regress allocated:iters --json FILE +RTS -T'` and check the module haddock's numbered properties (`bench/ConvVjpBench.hs:96` --- deliberately this file's one line citation, which is what lets `--restamp` maintain the stamp above) with `python3 tools/check-conv-bench-props.py FILE`, which checks every one of them twice, against seconds per iteration to 10% and against bytes allocated per iteration to 5%; the haddock classifies whether a failure means a broken measurement, an engine regression, or a legitimately shifted cost model. A green run is not the same as nothing having moved: all fifteen relations compare variants inside one group, so a variant family that shifts together satisfies every one of them. Orthotope's 2026-08-28 dispatch is the case on record --- it moved allocation across most of the suite, mostly downward and by a percent or two, while executing the *handwritten* dInp term went the other way and much further, 6--18% more from `inp-24x24` up and growing with size (`H-exec`, `H-exec-raw`, `H-fullpipe`; `H-term`, which only builds the term, did not move at all) --- and the suite passed throughout, property 6 in fact passing more easily for it. So diff a run against the recorded per-iteration figures under `bench/`, with `python3 tools/bench-baseline.py --baseline TSV JSON...`: it reads allocation, which is exact and moves only when the program does, and orders what moved by magnitude, the median mover across a real build change sitting under 1%. A green checker answers a different question. `--baseline` is required and has no default, because the files differ in suite and in which orthotope they link, nothing in a criterion JSON records either, and the benchmark names match across builds --- so a defaulted reference would report a whole build's difference as movement; the script's docstring lists them. Each of the three suites has a pair, `baseline-SUITE.tsv` against the sibling checkout and `baseline-SUITE-released.tsv` against Hackage orthotope, the released three being the anchors that survive the PR branch churning and the only ones a CI number can be read against. Refresh one only from a quiet-machine run and in the commit that explains what moved, so the figures and the reason land together. Every option matters: the checker reads the per-iteration OLS slope criterion prints on its `time` line, which `--csv` does not carry (it holds only the mean, which the warm-up ramp inflates per benchmark); `--regress allocated:iters` and `+RTS -T` are what the allocation pass reads, and it looks that regression up unconditionally, so without them the checker exits on the first report in either mode; and the raised time limit is what leaves a slow benchmark enough samples for that slope to converge --- at the default 5s the slowest land 8--11% low, the rest of that set within 6% either way. The checker gates on that itself, failing ahead of the properties on any slope fitted over too few samples or too poorly, so a collection that was too short says so rather than quietly shifting a property. What drove the raised limit is a handful of slow benchmarks, not the suite: at ~700ms per iteration the three `cnn-24x24` ones collected four samples at the default and eight at `-L 30`, both under the ten-sample gate, and only `-L 90` cleared it, at fifteen --- their R2 stays above 0.99 throughout, so the sample count alone gave them away --- and `inp-192x192`, `192x192` and `cnn-12x12` were the next worst --- the gate names whichever fell short, so there is no list to keep. Those groups were also the only ones that *needed* the long budget, though the checker's long-budget selection is wider: `gather48` and `scatter48` ride along so that the property comparing them is not fitted from one converged slope and one ramp-biased one. The checkout's `toVectorListT` work has since taken `cnn-24x24` to ~225ms, where `-L 30` gives it fifteen samples too, and the documented split now leaves nothing near either threshold, its worst standing at 21 samples and R2 0.994 (2026-08-28). Keep the budgets and the split anyway: the partition fixes each file's roster, a roster change moves numbers through the position effect the A/B rules below turn on, and shortening `cnn-24x24` would buy four minutes at the price of re-collecting every figure recorded against this recipe. So the checker takes several JSON files and merges them, letting `cnn-24x24` run longest, the other slow groups long and the rest run at the default, for about 30 minutes against the near three hours one run at `cnn-24x24`'s budget costs; its docstring holds the three selections, which have to partition the suite and must not cut across a property. Do not instead exclude the slow benchmarks from the checks: they carry 16 of the 84 property instances, every one of them at the sizes where gathers dominate and a rewrite can show up at all, so dropping them would leave a green run that verified nothing at scale.

The allocation half of that is what CI gates on, through `--allocation-only`: allocation is so nearly exact in the iteration count that even the sparsest-sampled `cnn-24x24` benchmarks fit it at R2 1.000000, so a default-limit collection gives an allocation verdict as good as a long-budget one, where the time slopes would need the raised limits above. `lint-and-test-suites.yml` therefore runs the whole suite that way on every push and checks the properties over allocation alone, which also leaves bytes allocated per iteration for every benchmark --- criterion prints it as the `iters` line under each `allocated:` block --- in a log GitHub keeps for ninety days, the point of printing them being to date a number that has started looking bad, nothing else here recording what allocation was months back. Those logs are a series only among themselves: CI resolves orthotope from Hackage where a local run may link the sibling checkout, so a CI number never compares with a local one, and a new orthotope release steps the whole series. What allocation cannot see is the standing caveat: the ~9--12x gather-against-scatter time gap is most of why the time properties exist --- a gap measured against orthotope 0.1.8.0 and closed by the strided-fallback work `.claude/rules/performance-model.md` records, which has now run through three checkout forms: as of 2026-08-28 it is 1.12x in gather's natural orientation and 1.01x against its `shn`-sorted one, with gather's `vec` orientation 1.14x ahead of scatter outright. Which orthotope the sibling checkout is on therefore moves the two-gather chains severalfold, so record it with any number taken here --- the released-against-`bq-expand` A/B covered `gather48` and `scatter48` only, where 4 of 13 benchmarks moved severalfold, 4 moved ~0.85x the other way at byte-identical allocation (the fused gathers --- a position effect of RTS pool state, `docs/position-effect.md`, not the fix; the same allocation test classifies the next one as real, and by 2026-08-28 it classifies the fused gathers themselves as reached, so they are no longer the unaffected control that A/B used), one scatter moved 1.24x at 1.23x the allocation (`two-scatters-ad-shn-sorted`, the only scatter carrying compensating transposes and so the only one whose slice views reach this fallback), and 4 not at all. A conv group was then measured on the same two builds: the dKrn sweep's `S-exec` ran 1.6x faster at `6x6` and 3.5--4.2x from `24x24` up, at 2.1--6.5x less allocation. Neither A/B has been repeated on the shipped fill, which is measured against the release nowhere. Refuted, and not to be reopened without new evidence: moving the suite to tasty-bench --- its estimator resists the ramp better, being an origin-forced two-point fit that discards the small-iteration measurements and stops on precision rather than on a clock, but it keeps only two measurements and so could not have produced the per-sample evidence these rulings rest on, and every recorded number would need re-collecting; dropping the 192 groups, when the slowest benchmarks in the suite lie outside them, in `cnn-24x24`; and trimming variants within a size, which breaks the pairwise-comparability design and several of the properties, and in fact aborts the checker outright.

The `cnn-*` groups consume `cnnObjective`, the objective they share with a printed-AST test; the reasoning about that sharing, and about refreshing the test when the simplifier moves, is in `test/CLAUDE.md`, which a session loads when working under `test/`.

## Writing a benchmark

- **An A/B across two *builds* needs interleaving and controls, because recompilation itself moves numbers.** Two binaries differing by a one-line toggle shift *unaffected* benchmarks by +/-2--5% (code-layout/codegen noise; the artifact can be larger and need not shrink with size --- the `NotShared` prod benches run measurably slower on a build carrying a rule their `cgrad` pipeline never reaches, and that gap *grows* with product length, ~4%/15%/22% at 100/1000/10000, the three sizes those benches exist at, a per-iteration placement effect rather than a fixed small-scale one; a dead-rule-guard rebuild returns toward baseline but only weakly corroborates, the compiler being free to drop the always-false guard), and batched runs (all A, then all B) additionally confound with time/thermal drift. Run interleaved A/B pairs (drift cancels within a pair) and include per-pair controls: a suite the change provably cannot affect (e.g. the concrete `VTA` MNIST groups of `BenchMnistTools` for a `contractAst` change --- the concrete pipeline never runs it), and/or a change-independent variant (e.g. `S-exec-raw` for a `contractAst` change: the raw artifact is contraction-independent --- see the `vjpArtifact` cost fact in `.claude/rules/performance-model.md` --- so it is identical across the toggle). The change's effect is the target's per-pair ratio minus the control's.
- **An A/B also needs the same benchmark selection in every run compared, and its decisive numbers taken one benchmark per process: a predecessor's leftover RTS pool state can shift a follower's time ~7--10% at the `-A32m` the suite now runs at, and did 22% at `-A1G`.** Interleaving and controls cannot catch it, both arms of a pair sharing their roster, and pinning alone is not sufficient when the compared builds change a predecessor's own allocation profile. Mechanism, evidence and the practical trade-offs are in `docs/position-effect.md`.
- **The nursery is `-A32m` by decision (2026-08-21, the root `CLAUDE.md`'s Tests section), not a knob to tune per ramp or per benchmark.** Measured there 2026-08-22, the move wanted no recalibration after all: every numbered property holds, in time and in allocation, and allocation per iteration is unmoved by the area, so what CI gates was never at risk. `inp-192x192`'s `H-*` variants do promote as predicted from `-A64m`, three of the four slowing 1.71--1.97x at GC 6.6--7.4% of wall against 0.02--0.03% and one to two gen-1 collections per iteration against none, while `H-term` stays nursery-local and runs faster; property 6 (`S-exec <= H-exec`) survives that inflation on its merits rather than spuriously, `S-exec` winning at `-A1G` too. `-A1G`, the previous setting, lost on every axis measured --- `docs/speculative-todos.md` holds the evidence.
- **Benchmark inputs must be random, not broadcast constants.** A constant input like `treplicate ... (sscalar 7)` is a stride-0 broadcast that the simplifier constant-folds *through* the very operations you mean to time --- a CNN gradient benchmark with a constant glyph lost its im2col gathers to folding and under-measured 24ms vs the honest 158ms. Use `randomValue`; a constant is only right when the *test* (e.g. a printed-AST test) wants a canonical small term.
