# Benchmark guidance (`bench/`)

Six criterion suites: five built over `bench/common/` (`BenchMnistTools`, `BenchProdTools`), and `convVjpBench`, which stands alone on `bench/ConvVjpBench.hs` over the test and example sublibraries. How to *invoke* them, which of them CI runs, and the rules for reasoning about the numbers afterwards are in the root `CLAUDE.md` — running `cabal bench` from the repo root does not load this file, which arrives only when a session opens something under `bench/`. What follows is for writing and reading the benchmarks themselves.

The names cited here — suites, criterion groups, cabal flags, functions — were verified against the tree at commit `d282ed596` (2026-07-31); the reference pass proves a cited name exists, this stamp that it still does what the claim around it needs. The wording differs from the stamp in `CLAUDE.md` and in `test/CLAUDE.md`, the latter split out of the root file in the same commit as this one, because this file cites no line numbers.

## `convVjpBench`

The `convVjpBench` benchmark (`bench/ConvVjpBench.hs`; not built under the `release` flag) is the [#123](https://github.com/Mikolaj/horde-ad/issues/123) diagnostic: `conv2dPreservingS` gradient wrt kernel and wrt input (dKrn/dInp) sweeps at 6–192, the symbolic and handwritten pipelines decomposed into pairwise-comparable `S-*`/`H-*` stage variants, `gather48`/`scatter48` isolating micro-benchmarks, `cnn-*` groups timing a real shaped two-layer CNN gradient, and a `pitfalls` group with the suite's single recorder of each known measurement trap (artifact hoisting, constant-cotangent embedding).

Those concept names are not the criterion path, which trips up filtering: dKrn is the bare size groups (`6x6` … `192x192`, built by `benchesAt`) and dInp the `inp-*` ones (`benchesInpAt`), with the stage variants as the bench names under each — so a run is picked out as `6x6/S-exec` or `-m glob "*/S-exec"`, never as `dKrn`, which appears in the source only as a comment and as the imported `conv2dPreserving_dKrn`. It uses only random data (`randomValue`), so it needs no `samplesData` and runs anywhere; `PRINT_TERMS=1` prints the compared gradient programs instead of benchmarking.

As the repo's only convolution-performance benchmark (the MNIST bench suites cover only FCNN nets) it outlives [#123](https://github.com/Mikolaj/horde-ad/issues/123): run it, with full criterion statistics, whenever touching conv-relevant code (gather/scatter rewrites in `contractAst`, the interpreter, the ox-arrays gather path) — the CI smoke run collects none. To analyze a run, collect it with `--benchmark-options='-L 30 --regress allocated:iters --json FILE +RTS -T'` and check the module haddock's numbered properties with `python3 tools/check-conv-bench-props.py FILE`, which checks every one of them twice, against seconds per iteration to 10% and against bytes allocated per iteration to 5%; the haddock classifies whether a failure means a broken measurement, an engine regression, or a legitimately shifted cost model. Every option matters: the checker reads the per-iteration OLS slope criterion prints on its `time` line, which `--csv` does not carry (it holds only the mean, which the warm-up ramp inflates per benchmark); `--regress allocated:iters` and `+RTS -T` are what the allocation pass reads, and it looks that regression up unconditionally, so without them the checker exits on the first report in either mode; and the raised time limit is what leaves a millisecond-scale benchmark enough samples for that slope to converge — at the default 5s it lands roughly 10–15% low. The checker gates on that itself, failing ahead of the properties on any slope fitted over too few samples or too poorly, so a collection that was too short says so rather than quietly shifting a property. What drives the raised limit is a handful of slow benchmarks, not the suite: at ~300ms per iteration the three `cnn-24x24` ones collect four to five samples at the default and fit at R² 0.918–0.989 — the last of those above the R² gate, so only its sample count gives it away — and `inp-192x192`, `192x192` and `cnn-12x12` are the next worst — the gate names whichever fell short, so there is no list to keep. Those groups are also the only ones that need the long budget, so the checker takes several JSON files and merges them, letting the slow groups run long and the rest run at the default for about 26 minutes against 54; its docstring holds the two selections, which have to partition the suite and must not cut across a property. Do not instead exclude the slow benchmarks from the checks: they carry 16 of the 84 property instances, every one of them at the sizes where gathers dominate and a rewrite can show up at all, so dropping them would leave a green run that verified nothing at scale.

The allocation half of that is what CI could gate on, and `--allocation-only` exists for it: allocation is so nearly exact in the iteration count that even the four-sample `cnn-24x24` benchmarks fit it at R² 1.000000, so a ten-minute default-limit collection gives an allocation verdict as good as an hour-long one, where the time slopes would need `-L 30`. Nothing wires it into CI yet — that is a decision about every push, not just about this suite. What allocation cannot see is the standing caveat: the ~9–12× gather-against-scatter time gap is most of why the time properties exist. Refuted, and not to be reopened without new evidence: moving the suite to tasty-bench — its estimator resists the ramp better, being an origin-forced two-point fit that discards the small-iteration measurements and stops on precision rather than on a clock, but it keeps only two measurements and so could not have produced the per-sample evidence these rulings rest on, and every recorded number would need re-collecting; dropping the 192 groups, when 7 of those 17 benchmarks lie outside them, including the three worst; and trimming variants within a size, which breaks the pairwise-comparability design and properties 2, 5 and 6.

The `cnn-*` groups consume `cnnObjective`, the objective they share with a printed-AST test; the reasoning about that sharing, and about refreshing the test when the simplifier moves, is in `test/CLAUDE.md`, which a session loads when working under `test/`.

## Writing a benchmark

- **An A/B across two *builds* needs interleaving and controls, because recompilation itself moves numbers.** Two binaries differing by a one-line toggle shift *unaffected* benchmarks by ±2–5% (code-layout/codegen noise; the artifact can be larger and need not shrink with size — the `NotShared` prod benches run measurably slower on a build carrying a rule their `cgrad` pipeline never reaches, and that gap *grows* with product length, ~4%/15%/22% at 100/1000/10000, the three sizes those benches exist at, a per-iteration placement effect rather than a fixed small-scale one; a dead-rule-guard rebuild returns toward baseline but only weakly corroborates, the compiler being free to drop the always-false guard), and batched runs (all A, then all B) additionally confound with time/thermal drift. Run interleaved A/B pairs (drift cancels within a pair) and include per-pair controls: a suite the change provably cannot affect (e.g. the concrete `VTA` MNIST groups of `BenchMnistTools` for a `contractAst` change — the concrete pipeline never runs it), and/or a change-independent variant (e.g. `S-exec-raw` for a `contractAst` change: the raw artifact is contraction-independent — see the root `CLAUDE.md`'s `vjpArtifact` cost fact — so it is identical across the toggle). The change's effect is the target's per-pair ratio minus the control's.
- **Don't shrink the nursery to buy off the first-touch ramp.** `exe-options` bakes in `-A1G`, and its page-fault cost is real: a 200-iteration run of `inp-192x192/S-exec-raw` takes 732k minor faults and 1.13s of system time, 532k and 0.87s of that the benchmark's own rather than the shared setup's, and 19% of wall, plus a warm-up ramp that makes criterion's early low-iteration samples wildly slow. It is nonetheless confined to that ramp and does not bias the converged slope — 21.89ms at `-A1G` against 21.91ms at `-A64m`, both `-L 60`. Giving the suite `-A64m` was tried and refuted: `inp-192x192`'s uncontracted term (`hTermVar`, forced at group setup and live across every benchmark in the group) exceeds 64MB, so three of its four `H-*` variants promote instead of dying in the nursery and slow by 2.1–2.4× (`bytesCopied` 13–25MB against 0.3MB, GC 5–6% of wall against 0.02%), and since property 6 reads `S-exec <= H-exec`, inflating `H-exec` makes a property pass spuriously. The two benchmarks that appeared to gain were the `cnn-24x24` ones whose baseline had four samples at R² 0.92, i.e. no baseline at all. Intermediate sizes do not rescue it: promotion stops by `-A256m` (0.6MB copied, GC 0.04%), yet three interleaved pairs still put `-A256m` 4.6% above `-A1G` on `H-exec` — 32.31ms against 30.90ms, where the `-A1G` runs repeat to 0.2% — because at 246MB allocated per iteration a 256MB nursery collects about once per iteration against once per four, and the fixed per-collection cost survives having nothing to copy; `-A128m` is worse again, 25% slower with 20–28MB copied. The penalty shrinks monotonically toward `-A1G`, so the largest nursery is the accurate one and the ramp is its price. Any future nursery change has to be shown harmless across the whole suite, not on the one benchmark that motivated it.
- **A setup warm-up does not remove the ramp either.** Running each `Benchmarkable` once before `defaultMain`, through criterion's own runner so that no `env`-style sharing is introduced, was implemented and measured across two interleaved pairs: nothing moved. First samples fell 2% at best (66.3ms to 64.7ms on `inp-192x192/S-exec-raw`), sample counts and R² came out identical, and the mean-to-slope gap stayed where it was, 57% against 55%. The cost is not a first-iteration cost: net of the setup baseline, that benchmark's own minor faults run 42k at one iteration, 276k at ten, 366k at twenty and 532k at fifty, then flat — so one warm iteration pays 8% of it and paying the rest needs about 35, which is 770ms per benchmark there and 11.5s each for `cnn-24x24`, minutes across the suite. Any warm-up cheap enough to run covers a sliver of it, while `-L 30` regresses the whole thing out for nothing. The guard for such an experiment, incidentally, is allocation per iteration: it must stay identical, or the warm-up has been shared with the measured expression and the benchmark is timing an already-evaluated value.
- **Benchmark inputs must be random, not broadcast constants.** A constant input like `treplicate … (sscalar 7)` is a stride-0 broadcast that the simplifier constant-folds *through* the very operations you mean to time — a CNN gradient benchmark with a constant glyph lost its im2col gathers to folding and under-measured 24ms vs the honest 158ms. Use `randomValue`; a constant is only right when the *test* (e.g. a printed-AST test) wants a canonical small term.
